== Active known issues

* *RSpamd milter connection is broken.* Postfix is configured to hand mail to RSpamd via milter on `mail.spam.milter_port` (`roles/mail/templates/postfix/main.cf.j2`, `roles/spam` controller config), but the connection is not working correctly yet — under active troubleshooting. Because `milter_default_action = accept`, mail still flows while this is broken, but spam filtering is effectively bypassed until it's fixed. Worth checking `rspamd` worker-controller/normal-worker binding vs. the port Postfix connects to, and `journalctl`/`rspamd` logs for the actual connection failure once reproducible.

== Missing functionality

* *DNS role doesn't serve the zone yet.* The `dns` role currently only sets up `unbound` as a loopback caching/validating resolver. Serving the `drehtuer.net`/`drehtuer.de` zone authoritatively (zone data, public listener) is planned but not started; the firewall's UDP/53 rule is already in place in preparation for this. Implement zone serving in `unbound` (or decide it belongs on a different host/provider and drop the pre-opened rule) once ready.
* *DKIM/SPF not enabled.* `roles/spam/tasks/main.yml` has DKIM key generation, DKIM signing, SPF, and a few other RSpamd module configs fully written but commented out. Outbound mail is currently unsigned, which will hurt deliverability. Uncomment/finish this once DNS TXT record publishing for DKIM/SPF is worked out (relevant to the DNS zone item above), and once the milter connection issue above is resolved.
* *Nextcloud first-run setup isn't automated.* `roles/cloud/tasks/main.yml` downloads, extracts, and wires up nginx/PHP-FPM/MariaDB for Nextcloud, but never runs the installer (`occ maintenance:install`), so there's no `config.php`, no admin account, no `trusted_domains`, and no Redis caching configured for it even though a Redis instance is already provisioned in `database`. Automate the `occ` install step (via `command`/`shell` with a `creates:` guard on `config.php`) and wire Redis into Nextcloud's config for file locking/caching.
* *`drehtuer.de` is not served yet.* The secondary domain is to be migrated to `carcosa.drehtuer.net` first, so it is deliberately absent from the certificate and from every vhost. The roles are already multi-domain: once the migration is done, adding it to `http.domains` in `inventories/host_vars/carcosa/http.yml` extends the certificate and every static vhost, plus the `cloud` vhost, with no template changes. `domain_aliases` in `inventories/machines.yml` still records it and is otherwise unused.
* *Nextcloud upgrades are not automated.* The role installs a pinned release but refuses to touch an existing installation, since unpacking over a live one without `occ upgrade` breaks it. Bumping `cloud.nextcloud.version` is therefore only effective on a fresh host. Automating the upgrade path (maintenance mode, extract, `occ upgrade`, `occ db:add-missing-indices`) belongs with the `occ` install item above.
* *No backup strategy.* Nothing in the repo backs up the MariaDB databases, Nextcloud data directory, mail spool, or vault-encrypted secrets to off-host storage. Given the stated migration/disaster-recovery goal, this is probably the single biggest gap.

== Future work (not urgent)

* *No umbrella playbook.* There is a `playbooks/<role>.yml` per role but nothing that runs them all in the right order for a fresh host (e.g. `system`/`apt`/`users` before service roles). Running playbooks individually is the deliberate workflow for now (easier to test each role in isolation while the configuration is still being built, and a full reinstall isn't currently needed). Worth adding a `playbooks/site.yml` (or an `invoke` task that chains the individual playbooks in order) once the roles have settled, so a full rebuild becomes a single command — relevant to the repo's migration goal, but not blocking current work.
* *Docker role has no consumer yet.* `roles/docker` installs Docker/Compose as deliberate groundwork for a future dockerized service. Nothing to do here until that service is chosen. When one is added, remember that publishing a port needs a matching entry in `firewall.docker.published` — `INPUT` does not apply to container traffic, so an unlisted published port is dropped by `DOCKER-USER` (and, before that chain existed, would have been exposed regardless of the firewall).

== Verify / likely bugs

* *Certificate lineage may need a one-off fix on the host.* The `http` role now pins the lineage to `--cert-name {{ http.letsencrypt.cert_name }}`, but certbot previously derived it from the first `-d` (`drehtuer.net`) while every consumer read `/etc/letsencrypt/live/carcosa.drehtuer.net/`. If a `drehtuer.net` lineage already exists on the host, check `certbot certificates` and either rename it or delete it and reissue, otherwise two lineages will be renewed in parallel.
* *Checksum `when` guard compares the wrong value.* In `roles/spam/tasks/main.yml`, `spam_htpasswd_checksum != spam.htpasswd_sha256` compares the *entire* `ansible.builtin.stat` result object against a plain sha256 string instead of `<var>.stat.checksum`. A dict is never equal to a string, so the condition is always true and the intended "only copy if the checksum changed" gating doesn't gate anything (`copy`'s own idempotency still prevents spurious "changed" reports, but the explicit check is dead logic). The same bug was removed from `roles/sshd` by deleting the probe outright, since `copy` already compares content — the same fix probably applies here.
* *`nginx-404` filter is unverified.* `roles/fail2ban/files/filter.d/nginx-404.conf` is written against the `main` log format in `roles/http/files/nginx.conf`, but has not been run against real log lines. Check with `fail2ban-regex /var/log/nginx/access.log /etc/fail2ban/filter.d/nginx-404.conf`; a filter that matches nothing fails silently.
* *`firewall.docker.wan_interface` is fact-derived.* It resolves to `ansible_default_ipv4.interface`. Confirm that is the real internet-facing NIC on `carcosa` — a wrong interface means the `DOCKER-USER` drop never matches and published container ports are exposed, with no visible error. Pin it explicitly in the inventory if the fact is not dependable.
* *fail2ban's ban action vs. the firewall.* The `firewall` role restarts fail2ban after every rules reload, because `iptables-restore` flushes the `filter` table and with it every `f2b-*` chain. This assumes fail2ban is using an `iptables` ban action. If the installed version defaults to the `nftables` action instead, its chains live elsewhere, survive the flush, and the restart is unnecessary (harmless, but worth knowing). Check with `iptables -S | grep f2b` after a firewall run.

== Documentation gaps

* No day-2 operations runbook: how to rotate the vault password, rotate a compromised user/mail password, restore a host from scratch, add a second host, or renew/replace host SSH keys.
* No documented backup/restore procedure (depends on the backup strategy item above).
* `doc/environment-setup.adoc` covers the Dev Container only — there's no doc for the target *production* host prerequisites (base OS version/image, disk layout, initial bootstrap access before Ansible can connect, DNS delegation setup for the zone/aliases).
* No changelog or versioning convention for the infrastructure itself (e.g. how config drift or emergency manual changes on the host get reconciled back into the repo).

== Process / quality

* *No cross-role or full-stack testing.* Static tests and molecule both check a role in isolation, but the bugs that have cost the most here were interactions between roles: `iptables-restore` flushing fail2ban's chains, the `http` certificate bootstrap deadlocking against nginx, a certificate lineage name disagreeing with what three other roles read. Catching those needs `playbooks/site.yml` (see above) plus a run against a throwaway VM — a Hetzner instance created and destroyed per run costs about half a cent, so this can be automated even though production cannot. Verification with `goss` or `testinfra`: ports listening, TLS chain valid, SMTP banner, and `fail2ban-client status <jail>` for the jails. See `doc/TESTING.adoc`.
* *Molecule covers three roles.* `apt`, `cron` and `users`. `sshd` needs unencrypted test host keys before it can be added, `time` needs the `hwclock` handler to be skippable in a container, and `system` needs the hostname task to tolerate not having the capability. The rest need a VM. Each blocker is listed in `doc/TESTING.adoc`.
* Nothing checks that a freshly provisioned host actually serves HTTPS, accepts mail or resolves DNS. Molecule proves a role converges and is idempotent; it says nothing about whether the service works. This is the same gap as the full-stack item above.
* Only one real host (`carcosa`) is defined in `inventories/machines.yml`. Since the explicit goal of this repo is easy migration to a new server, a from-scratch provision has never actually been proven end-to-end. (`inventories/test/` is not this: it is fake data for the tests and is never deployed.)
