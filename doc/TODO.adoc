== Active known issues

* *RSpamd milter connection is broken.* Postfix is configured to hand mail to RSpamd via milter on `mail.spam.milter_port` (`roles/mail/templates/postfix/main.cf.j2`, `roles/spam` controller config), but the connection is not working correctly yet — under active troubleshooting. Because `milter_default_action = accept`, mail still flows while this is broken, but spam filtering is effectively bypassed until it's fixed. Worth checking `rspamd` worker-controller/normal-worker binding vs. the port Postfix connects to, and `journalctl`/`rspamd` logs for the actual connection failure once reproducible.

== Missing functionality

* *DNS role doesn't serve the zone yet.* The `dns` role currently only sets up `unbound` as a loopback caching/validating resolver. Serving the `drehtuer.net`/`drehtuer.de` zone authoritatively (zone data, public listener) is planned but not started; the firewall's UDP/53 rule is already in place in preparation for this. Implement zone serving in `unbound` (or decide it belongs on a different host/provider and drop the pre-opened rule) once ready.
* *DKIM/SPF not enabled.* `roles/spam/tasks/main.yml` has DKIM key generation, DKIM signing, SPF, and a few other RSpamd module configs fully written but commented out. Outbound mail is currently unsigned, which will hurt deliverability. Uncomment/finish this once DNS TXT record publishing for DKIM/SPF is worked out (relevant to the DNS zone item above), and once the milter connection issue above is resolved.
* *Nextcloud first-run setup isn't automated.* `roles/cloud/tasks/main.yml` downloads, extracts, and wires up nginx/PHP-FPM/MariaDB for Nextcloud, but never runs the installer (`occ maintenance:install`), so there's no `config.php`, no admin account and no `trusted_domains`. Automate the `occ` install step (via `command`/`shell` with a `creates:` guard on `config.php`). Caching is no longer part of this item: APCu and Redis are configured through `config/cache.config.php`, an additional config file the role owns independently of `config.php` (see `doc/STATUS.adoc`).
* *`drehtuer.de` has never been deployed.* It is now in `http.domains` (derived from `domain_aliases`), so the next `playbooks/http.yml` run expands the certificate to it and serves every subdomain. Before that run, the Hetzner zone for `drehtuer.de` needs A/AAAA records pointing at this host for the bare domain and for `cloud`, `mail`, `spam`, `status` and `www` — certbot validates each name over HTTP-01, and one failing challenge fails the whole certificate, including the renewal of the names that already worked. Deploy order is `http` first, then `cloud`/`spam`/`mail`.
* *Nextcloud upgrades are not automated.* The role installs a pinned release but refuses to touch an existing installation, since unpacking over a live one without `occ upgrade` breaks it. Bumping `cloud.nextcloud.version` is therefore only effective on a fresh host. Automating the upgrade path (maintenance mode, extract, `occ upgrade`, `occ db:add-missing-indices`) belongs with the `occ` install item above.
* *No backup strategy.* Nothing in the repo backs up the MariaDB databases, Nextcloud data directory, mail spool, or vault-encrypted secrets to off-host storage. Given the stated migration/disaster-recovery goal, this is probably the single biggest gap.

== Future work (not urgent)

* *No umbrella playbook.* There is a `playbooks/<role>.yml` per role but nothing that runs them all in the right order for a fresh host (e.g. `system`/`apt`/`users` before service roles). Running playbooks individually is the deliberate workflow for now (easier to test each role in isolation while the configuration is still being built, and a full reinstall isn't currently needed). Worth adding a `playbooks/site.yml` (or an `invoke` task that chains the individual playbooks in order) once the roles have settled, so a full rebuild becomes a single command — relevant to the repo's migration goal, but not blocking current work. Each playbook's role is already tagged with its own name (e.g. `apt`, `mail`) specifically so a future umbrella gets selective `--tags`/`--skip-tags` runs for free, without a follow-up pass through every playbook.
* *Every playbook still targets `hosts: all`.* The second host (`nyarlathotep`, see `doc/TESTING.adoc`) arrived before the playbooks were regrouped, so the inventory now has `production` and `testlab` groups but the playbooks themselves are unchanged. What keeps a run off the wrong machine is `invoke run-playbook` refusing to run without `--hosts` — a guard, not a fix. The fix is to give each playbook a group, which matters properly once a host exists that should *not* run every role (e.g. one that does no mail/spam/imap). Worth doing alongside the umbrella playbook above, since both touch the same files.
* *Docker role has no consumer yet.* `roles/docker` installs Docker/Compose as deliberate groundwork for a future dockerized service. Nothing to do here until that service is chosen. When one is added, remember that publishing a port needs a matching entry in `firewall.docker.published` — `INPUT` does not apply to container traffic, so an unlisted published port is dropped by `DOCKER-USER` (and, before that chain existed, would have been exposed regardless of the firewall).

== Verify / likely bugs

* *Top-level facts are deprecated.* `roles/upgrade/tasks/main.yml` reads `ansible_distribution` and `ansible_distribution_version`, and `roles/firewall/defaults/main.yml` reads `ansible_default_ipv4.interface`, as bare variables. ansible-core warns that `INJECT_FACTS_AS_VARS` will default to false, after which those become undefined: the upgrade role fails at its first assertion, and the firewall role renders an empty interface name into the `DOCKER-USER` rule - which fails open rather than loudly. Switch both to `ansible_facts['...']`. Surfaced by the first real run of the upgrade role on the test lab.
* *The 26.04 upgrade is gated by Ubuntu, not by this repo.* `upgrade.target_release` is ready and `hastur` exists to rehearse it, but `do-release-upgrade` will not offer 24.04 -> 26.04 until the 26.04.1 point release. Re-check with `do-release-upgrade -c`, rehearse on `hastur`, then run it against `carcosa`.
* *The `spam` vhost has never loaded.* It included `locations-enabled/letsencrypt.conf`, a file no role creates, which is a fatal `nginx -t` error. That include is gone, so the vhost will load for the first time on the next run — meaning `spam.<domain>` and the RSpamd controller UI behind it are effectively untested. Run `nginx -t` before deploying, so a pre-existing failure is not mistaken for a new one, and check the basic-auth prompt and the proxy to the controller afterwards.
* *Nextcloud `trusted_domains` is now role-owned and replaces what is in `config.php`.* The key in `config/domains.config.php` overrides the array the installer wrote rather than merging with it. If the running host trusts a name that the inventory does not produce, that name stops working on the next `playbooks/cloud.yml` run. Compare `occ config:system:get trusted_domains` against the rendered file before deploying.
* *Nextcloud now hard-depends on Redis.* `memcache.locking` in `config/cache.config.php` points at the shared Redis instance, so an unreachable Redis makes Nextcloud return errors rather than degrade. Both run on the same host and `playbooks/database.yml` provisions Redis, but on a fresh host it has to have run before `playbooks/cloud.yml` — one more ordering constraint for the umbrella playbook above. Confirm with `occ config:list system` and Nextcloud's admin overview after the first deploy that the cache is actually in use, since a misconfigured cache is reported as "not configured" rather than as an error.
* *Only the `apt` role refreshes the apt cache.* Every other role installs packages assuming it is already fresh, so running e.g. `playbooks/cron.yml` against a host where `playbooks/apt.yml` has never run fails with "No package matching 'cron' is available". The molecule scenarios surfaced this, because they converge a role on its own; they work around it with a `prepare.yml`. It has never bitten `carcosa` because `apt.yml` is always run first, and an umbrella `site.yml` (see *No umbrella playbook* above) would encode that ordering properly. The alternative — `update_cache` in every role — is slower and duplicated, so this is a decision to make rather than an obvious fix.
* *Certificate lineage may need a one-off fix on the host.* The `http` role now pins the lineage to `--cert-name {{ http.letsencrypt.cert_name }}`, but certbot previously derived it from the first `-d` (`drehtuer.net`) while every consumer read `/etc/letsencrypt/live/carcosa.drehtuer.net/`. If a `drehtuer.net` lineage already exists on the host, check `certbot certificates` and either rename it or delete it and reissue, otherwise two lineages will be renewed in parallel.
* *`nginx-404` filter is unverified.* `roles/fail2ban/files/filter.d/nginx-404.conf` is written against the `main` log format in `roles/http/files/nginx.conf`, but has not been run against real log lines. Check with `fail2ban-regex /var/log/nginx/access.log /etc/fail2ban/filter.d/nginx-404.conf`; a filter that matches nothing fails silently.
* *`firewall.docker.wan_interface` is fact-derived.* It resolves to `ansible_default_ipv4.interface`. Confirm that is the real internet-facing NIC on `carcosa` — a wrong interface means the `DOCKER-USER` drop never matches and published container ports are exposed, with no visible error. Pin it explicitly in the inventory if the fact is not dependable.
* *fail2ban's ban action vs. the firewall.* The `firewall` role restarts fail2ban after every rules reload, because `iptables-restore` flushes the `filter` table and with it every `f2b-*` chain. This assumes fail2ban is using an `iptables` ban action. If the installed version defaults to the `nftables` action instead, its chains live elsewhere, survive the flush, and the restart is unnecessary (harmless, but worth knowing). Check with `iptables -S | grep f2b` after a firewall run.

== Process / quality

* *No cross-role or full-stack testing.* Static tests and molecule both check a role in isolation, but the bugs that have cost the most here were interactions between roles: `iptables-restore` flushing fail2ban's chains, the `http` certificate bootstrap deadlocking against nginx, a certificate lineage name disagreeing with what three other roles read. Catching those needs `playbooks/site.yml` (see above) plus a run against a throwaway VM — a Hetzner instance created and destroyed per run costs about half a cent, so this can be automated even though production cannot. Verification with `goss` or `testinfra`: ports listening, TLS chain valid, SMTP banner, and `fail2ban-client status <jail>` for the jails. See `doc/TESTING.adoc`.
* *Molecule covers six roles.* `apt`, `cron`, `users`, `sshd`, `time` and `system`. See *Molecule roles needing a VM* below for the rest, and `doc/TESTING.adoc` for the container-only test-fixture and skip-tag patterns `sshd`/`system` use to stay container-testable without changing production behavior.
* *Molecule roles needing a VM.* Tracked here so they get picked up later rather than forgotten - see `doc/TESTING.adoc` for the per-role blocker:
** `firewall`, `docker` — need real netfilter / nested Docker.
** `http`, `cloud`, `mail`, `imap`, `spam`, `dns`, `database` — need real certificates and real cross-service communication. Self-signed certificates (rather than Let's Encrypt, which cannot work against a container or a throwaway VM without a real domain) are the planned approach once these are tackled - see also *No cross-role or full-stack testing* above, since several of these only really prove anything as part of a full-stack run.
** `upgrade` — runs `do-release-upgrade` and reboots; not meaningfully automatable in a container or a short-lived VM.
* Nothing checks that a freshly provisioned host actually serves HTTPS, accepts mail or resolves DNS. Molecule proves a role converges and is idempotent; it says nothing about whether the service works. This is the same gap as the full-stack item above.
* A from-scratch provision has still never been proven end-to-end. `nyarlathotep` (the `testlab` group) now allows the roles to be run against real hardware, which is a large step up from molecule, but that machine was already part-configured before it was adopted, so a green run there does not prove a bare Ubuntu install would reach the same state. Proving it needs a reinstall first — `lab.sh reinstall-stage`/`reinstall-arm` exist for that but are **unverified and can strand the machine**, since it has no remote console. (`inventories/test/` is not this either: it is fake data for the tests and is never deployed.)
