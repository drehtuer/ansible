== Active known issues

* *`rspamd-train-bulk` under-reports what it learned, and re-running it double-trains.* Seeding the classifier from the `drehtuer.de` migration on 2026-08-16 exposed this, and the failure mode is worse than it first looks. Its per-batch accounting is `grep` over `rspamc` output, and the three counts need not add up: the spam run reported `found 18237` then `learned 14268, skipped 65, failed 7`, leaving 3897 messages reported as nothing at all. That reads like "3897 were missed", and acting on it makes things worse — re-running the corpus to "recover" them drove `BAYES_SPAM` to *20144 learns against a corpus of 18237 unique messages*, so at least 1907 messages were learned twice and their tokens double-weighted. The likelier explanation is that the first pass *did* learn most of those 3897 but `rspamc` timed out before reporting (50 files per invocation against a Redis under load, with the response swallowed by `2>&1 || true`), so RSpamd wrote the tokens while the learn-cache entry that would have made a re-run a no-op was never written. The ham run over the same corpus balanced exactly (`11913 = 11778 + 135`), so this only appears under load. Three fixes, in order of importance: (1) never re-run a bulk seed to chase a shortfall — `Total learns` exceeding the corpus size is the symptom to check for; (2) count outcomes per *file* rather than by grepping a batch's aggregate output, and make a run that cannot account for every input message exit non-zero; (3) lower the batch size or raise `rspamc`'s timeout so the reports are trustworthy in the first place. Note also that `FAILED=$((FAILED + errors - benign > 0 ? errors - benign : 0))` does not accumulate at all — `>` binds tighter than `?:`, so it tests `FAILED + errors - benign > 0` and then *assigns* `errors - benign`, discarding the running total.

== Missing functionality

* *Publish the DS records, and only then is DNSSEC actually on.* Both zones have been signed since 2026-08-16 and the signed copies transfer to all three secondaries, but neither parent carries a DS record, so every validator still treats them as unsigned - the work so far is inert by design, which is what made it safe to deploy without a maintenance window. Finishing it means giving Hetzner the DS below for each domain and waiting for it to appear in the parent:
+
----
drehtuer.net. IN DS 43736 13 2 A2063E2191F71BD3F561C1D21E525F5291BCE400C5776A2670C470B23A11E5DD
drehtuer.de.  IN DS 51108 13 2 8EB48A3A121749C1E543CE9DE7EB46B59B49A409387D265594BEC0EBD3A09FA0
----
+
Do it in that order and not the other one. A DS published before the zone serves the matching DNSKEY does not degrade the zone, it makes it *bogus*, and validating resolvers refuse every answer - with `p=reject` DMARC on both domains that is mail and web at once. Verify after publishing with `delv @1.1.1.1 <domain> A`, which should report the answer as fully validated, and check that the AD flag comes back set; before publishing the same query resolves but is unvalidated. Note also that the weekly re-signing cron becomes load-bearing from this moment: until the DS exists, expired signatures would go unnoticed; afterwards they take the domain off the internet.
* *Publish DANE (TLSA) records for mail, once the zones are signed.* Nothing is published today — `dig TLSA _25._tcp.mail.drehtuer.net` returns nothing for either domain. This is *strictly blocked on the DNSSEC item above*: a TLSA record that a resolver cannot validate is not merely useless, it is ignored, so DANE without DNSSEC buys nothing at all. Worth recording now because the two are usually decided together, and because the operational hazard is in the renewal rather than the setup. A `3 1 1` record pins the leaf public key, and certbot generates a *new* key on renewal unless `--reuse-key` is set — so the record goes stale at the next renewal and receiving mail servers that honour DANE stop delivering, silently and only for them. Pinning the issuer with `2 1 1` avoids that but moves the problem to Let's Encrypt's intermediate rotation. Whichever is chosen, it is per name and per domain, and every change needs its zone serial bumped — see the first item in this section, which becomes load-bearing rather than advisory once mail delivery depends on the record being current.
* *Remove the superseded `mail._domainkey` records, not before 2026-09-16.* DKIM was rotated to selector `s202608` (RSA-2048) on 2026-08-16 and verified end to end — `R_DKIM_ALLOW` against live DNS for both domains. The old `mail._domainkey` records are still published on purpose, so that any message signed before the switch still verifies; `drehtuer.net`'s is the ed25519 one that prompted the rotation, `drehtuer.de`'s an RSA key that was fine and got rotated only because the selector is global. A month is far longer than any message stays in flight and costs nothing, so there is no reason to hurry. Delete both records from `nsd.zones`, bump both serials, re-run `nsd.yml`; the orphaned `*.mail.key` files on the host can go at the same time. The remaining commented tasks - `spf.conf`, `dkim.conf`, `groups.conf` - are only module tuning; those modules already run without them.
+
Worth doing once for its own sake: send a message from each domain to a checker such as `check-auth@verifier.port25.com`. The round-trip above proves the signature verifies, but RSpamd signed *and* verified it, so a second implementation confirming it — along with SPF and DMARC alignment as a receiver actually evaluates them — is a stronger result than this repo can produce on its own.
* *Nextcloud first-run setup isn't automated.* `roles/cloud/tasks/main.yml` downloads, extracts, and wires up nginx/PHP-FPM/MariaDB for Nextcloud, but never runs the installer (`occ maintenance:install`). On `carcosa` that step was done by hand, so the host is fine - `occ status` reports `installed: true` on 34.0.3 - and the gap is felt only when building the *next* host from this repo, which is exactly the migration/disaster-recovery goal. Automate the `occ` install step (via `command`/`shell` with a `creates:` guard on `config.php`).
* *Nextcloud upgrades are not automated.* The role installs a pinned release but refuses to touch an existing installation, since unpacking over a live one without `occ upgrade` breaks it. Bumping `cloud.nextcloud.version` is therefore only effective on a fresh host. Automating the upgrade path (maintenance mode, extract, `occ upgrade`, `occ db:add-missing-indices`) belongs with the `occ` install item above.
* *No metrics, statistics or monitoring of any kind.* Nothing is installed — no `snmpd`, no Prometheus exporters, no collectd or telegraf — so there is no history of load, disk, mail volume, spam rates or certificate expiry, and nothing that would notice a service degrading before it fails outright. Note that a home for this already exists and is unused: `status.<domain>` resolves, is covered by the certificate, and currently returns 200 from the static document root, i.e. a placeholder with nothing behind it. SNMP is one route and the most portable one; the alternative is `node_exporter` plus the per-service exporters that Postfix, Dovecot, nginx and RSpamd all have, scraped and rendered behind that vhost. Either way two lessons already recorded here apply: anything containerised wants the `network_mode: host` plus loopback bind that `roles/fail2ban_ui` uses rather than a published port, and whatever ends up listening needs deciding against `roles/firewall` rather than left to default.
* *No backup strategy.* Nothing in the repo backs up the MariaDB databases, Nextcloud data directory, mail spool, or vault-encrypted secrets to off-host storage. Given the stated migration/disaster-recovery goal, this is probably the single biggest gap.

== Future work (not urgent)

* *No umbrella playbook.* There is a `playbooks/<role>.yml` per role but nothing that runs them all in the right order for a fresh host (e.g. `system`/`apt`/`users` before service roles). Running playbooks individually is the deliberate workflow for now (easier to test each role in isolation while the configuration is still being built, and a full reinstall isn't currently needed). Worth adding a `playbooks/site.yml` (or an `invoke` task that chains the individual playbooks in order) once the roles have settled, so a full rebuild becomes a single command — relevant to the repo's migration goal, but not blocking current work. Each playbook's role is already tagged with its own name (e.g. `apt`, `mail`) specifically so a future umbrella gets selective `--tags`/`--skip-tags` runs for free, without a follow-up pass through every playbook. Four separate ordering constraints are waiting on it, all recorded below: `dns` before `spam`, `database` before `cloud`, `docker`/`fail2ban`/`http` before `fail2ban_ui`, and `apt` before everything.
* *Every playbook still targets `hosts: all`.* The second host (`nyarlathotep`, see `doc/TESTING.adoc`) arrived before the playbooks were regrouped, so the inventory now has `production` and `testlab` groups but the playbooks themselves are unchanged. What keeps a run off the wrong machine is `invoke run-playbook` refusing to run without `--hosts` — a guard, not a fix. The fix is to give each playbook a group, which matters properly once a host exists that should *not* run every role (e.g. one that does no mail/spam/imap). Worth doing alongside the umbrella playbook above, since both touch the same files.
* *Docker role has no consumer yet.* `roles/docker` installs Docker/Compose as deliberate groundwork for a future dockerized service. Nothing to do here until that service is chosen. When one is added, remember that publishing a port needs a matching entry in `firewall.docker.published` — `INPUT` does not apply to container traffic, so an unlisted published port is dropped by `DOCKER-USER` (and, before that chain existed, would have been exposed regardless of the firewall).
* *SMTP and IMAP authenticate with passwords only; client certificates were never considered.* Both ends already go through one place, which makes this smaller than it looks: Postfix delegates SASL to Dovecot (`smtpd_sasl_type = dovecot`, `smtpd_sasl_path = private/auth`), and Dovecot authenticates against system accounts (`passdb pam`, `userdb passwd`, `auth_mechanisms = plain login`). Moving to certificates means `auth_ssl_require_client_cert` and `auth_ssl_username_from_cert` in Dovecot, and both protocols follow. **The trap is the CA.** `imap.conf.ssl.ca` currently points at Let's Encrypt's chain because that is what serving the certificate needs; reusing it to *validate* clients would mean every certificate Let's Encrypt has ever issued authenticates as a local user. This needs a private CA of its own, with issuance, renewal and revocation to run — which is the real cost, not the Dovecot settings. Weigh also that client-certificate support in mail clients is uneven, especially on mobile, and that certificates-only means no fallback: a lost device is a lockout rather than a password reset.
* *No rendered documentation, though the docs were written for it.* Every page under `doc/` opens with `include::.attributes-page.adoc[]`, and that file already sets `:backend: html5`, `:data-uri:`, `:toc: auto` and a source highlighter — so the intent to render standalone HTML pages predates this note, and only the build and publish step is missing. Nothing renders them today: there is no asciidoctor invocation in `.github/`, `tasks.py` or `pyproject.toml`, and the only workflows are `lint.yml` and `test.yml`. A third workflow rendering `doc/*.adoc` to GitHub Pages would cost little and pay off most on `STATUS.adoc`, which is long, heavily cross-referenced and much easier to navigate with the table of contents it already asks for. Note there is no disclosure question to weigh: the repository is already public, so this changes how the documentation reads, not who can read it.

== Verify / likely bugs

* *`$myhostname` is listed in both `mydestination` and `virtual_mailbox_domains`.* Postfix advises against a domain being in both, and `mail.drehtuer.net` is in both. Pre-existing and untouched by the multi-domain work. Which address class actually wins is the very thing the warning says not to rely on, so establish it first — `postmap -q mail.drehtuer.net` proves nothing here; send a message to `root@mail.drehtuer.net` and see whether it lands in the Maildir or in `/var/mail`. Then decide which of the two lines should own the name rather than leaving the warning in the log. Removing `$myhostname` from `virtual_mailbox_domains` is the smaller edit, but it may move that name's delivery, so test it rather than assuming.
* *Nothing validates a recipient at SMTP time.* `virtual_mailbox_maps` is empty, so Postfix accepts any address in a `virtual_mailbox_domains` domain, hands it to Dovecot over LMTP, is refused there, and bounces it afterwards — backscatter, to a sender address that is often forged. Pre-existing for `drehtuer.net`; adding `drehtuer.de` doubles the surface without changing the shape of the problem. The fix is a `virtual_mailbox_maps` (or `local_recipient_maps`) that Postfix can check during the SMTP transaction, generated from the same account list `roles/users` already owns.
* *SPF/DKIM rejection is implemented but unverified.* `roles/spam/files/rspamd/force_actions.conf` rejects on `R_SPF_FAIL` and `R_DKIM_REJECT` and loads correctly, but the reject path was never exercised: the test lab is behind user-mode NAT and mails itself from a private address, so RSpamd produced no SPF or DKIM symbols at all. Confirm against real inbound mail on `carcosa` - a message from a domain publishing `-all` should be refused with the message in that file, and one from a domain with no policy should still be accepted.
* *Remove the inert OCSP stapling directives.* `roles/http/files/nginx.conf` sets `ssl_stapling on` and `ssl_stapling_verify on`, and nothing is ever stapled: Let's Encrypt has retired OCSP and the issued certificate carries no responder URI, so there is nothing for nginx to fetch. Confirmed on the host with `openssl s_client -connect drehtuer.net:443 -status` ("no response sent") and by reading the Authority Information Access extension, which holds a CA Issuers URI and nothing else. Not a bug in the sense of causing harm - the directives are simply dead - but they read as a working security feature to anyone auditing the file. Decide separately whether to keep the `resolver` line, which is not OCSP-specific.
* *The CSP still permits inline script and style.* `roles/http/files/security.conf` was narrowed from a policy that allowed any `http:`/`https:` origin to one scoped to this origin, but `'unsafe-inline'` remains for both script and style because the RSpamd web UI proxied at `spam.<domain>` includes the same file and needs them. Removing them means either giving that vhost its own policy or testing the UI in a browser afterwards - a 200 from `curl` does not prove the interface still works.
* *`roles/spam` depends on `roles/dns`.* `options.inc` points RSpamd's resolver at `127.0.0.1`, so without `unbound` every DNS-based check - SPF, DKIM, DMARC, RBLs - silently returns nothing. No error is logged; spam filtering just quietly does much less. Deploy `playbooks/dns.yml` before `playbooks/spam.yml` on a fresh host, and fold the ordering into the umbrella playbook when it exists.
* *`roles/cloud` depends on `roles/database`.* `memcache.locking` in `config/cache.config.php` points at the shared Redis instance, so an unreachable Redis makes Nextcloud return errors rather than degrade. Both run on the same host and `playbooks/database.yml` provisions Redis, so this is only an ordering constraint on a fresh host - one more for the umbrella playbook.
* *The fail2ban UI and `roles/fail2ban` both write `jail.local`.* A standing caveat rather than a pending check, and the same shape as the Nextcloud one below: the UI's Global Settings are written into that file's `[DEFAULT]` section, so anything changed through the web interface is reverted by the next `playbooks/fail2ban.yml` run. Change jails in `fail2ban.jails` and deploy; treat the UI as read-plus-ban rather than as a configuration editor. Starting the container does not itself touch the file — verified after deploying, `jail.local`'s mtime was unchanged and the fail2ban role reported no drift.
+
A way out exists and was deliberately *not* taken, on 2026-08-16 — recorded here so the research is not repeated. fail2ban reads its configuration in a fixed order, from `configreader.py`: `jail.conf`, then `jail.d/*.conf` sorted, then `jail.local`, then `jail.d/*.local` sorted, with later files overriding earlier ones. `jail.d/*.local` therefore outranks `jail.local`. Pointing this role's template at `/etc/fail2ban/jail.d/zz-ansible.local` (plus `state: absent` on the old `jail.local`, and the `zz-` prefix to stay last in a sorted glob) would make Ansible win every key it sets, immediately and deterministically, while leaving the UI usable for anything the role does not set. The template itself would not change — only the `dest`.
+
It was left alone because it trades one silent failure for another: today a UI edit applies and is then reverted at the next playbook run, whereas afterwards it would never apply at all, and the UI would still *display* its own `jail.local` values rather than the effective ones. Neither tells the operator anything. Going the other way is worse and should not be considered: `JAIL_AUTOMIGRATION=true` is the only setting upstream offers that moves the UI's writes, it is documented as "Experimental migration from a monolithic `jail.local` to `jail.d/*.local`. On production systems, migrate manually instead", and it would put the UI's file *above* Ansible's — inverting which system is authoritative. There is no read-only mode and no other write restriction in the image's configuration reference.
+
Worth re-checking when the UI is next upgraded: an upstream option to target a specific file, or a genuine read-only mode, would settle this properly and is the preferred outcome over either workaround.
* *`roles/fail2ban_ui` depends on `roles/docker`, `roles/fail2ban` and `roles/http`.* The engine and Compose v2, the socket it is a front end for, and nginx plus a certificate covering `fail2ban_ui.subdomain`. Nothing asserts this; it is one more ordering constraint for the umbrella playbook. Note also that `fail2ban_ui.subdomain` must appear in `http.letsencrypt.subdomains` or the vhost is served with a certificate that does not cover it — nothing enforces that pairing, exactly as with the `spam` role.
* *`roles/fail2ban` depends on `roles/http` having run at least once.* The `nginx-http-auth` and `nginx-404` jails point at `/var/log/nginx/*.log`, and fail2ban refuses to start at all when a jail's log file is missing - `ERROR Failed during configuration: Have not found any log file for nginx-http-auth jail`, then `status=255/EXCEPTION`. On a from-scratch provision `fail2ban.yml` runs before `http.yml`, so the service is left dead and `systemctl list-units --state=failed` does not read clean. Restarting it once nginx exists brings all six jails up, so this is ordering rather than configuration - one more constraint for the umbrella playbook, alongside `dns` before `spam` and `database` before `cloud`. Found on a from-scratch VM provision on 2026-08-16; it has never bitten `carcosa`, where nginx long predates the role.
* *Only the `apt` role refreshes the apt cache.* Every other role installs packages assuming it is already fresh, so running e.g. `playbooks/cron.yml` against a host where `playbooks/apt.yml` has never run fails with "No package matching 'cron' is available". The molecule scenarios surfaced this, because they converge a role on its own; they work around it with a `prepare.yml`. It has never bitten `carcosa` because `apt.yml` is always run first, and an umbrella `site.yml` (see *No umbrella playbook* above) would encode that ordering properly. The alternative — `update_cache` in every role — is slower and duplicated, so this is a decision to make rather than an obvious fix.
* *Nextcloud `trusted_domains` is role-owned and replaces what is in `config.php`.* A standing caveat rather than a pending check: the key in `config/domains.config.php` overrides the array the installer wrote rather than merging with it, so a name added to `config.php` by hand stops working on the next `playbooks/cloud.yml` run. Compare `occ config:system:get trusted_domains` against the rendered file before deploying a change to the domain list.
* *The 26.04 upgrade is gated by Ubuntu, not by this repo.* `upgrade.target_release` is ready and `hastur` exists to rehearse it, but `do-release-upgrade` will not offer 24.04 -> 26.04 until the 26.04.1 point release. See `doc/TESTING.adoc` for what the rehearsal proved. Re-check with `do-release-upgrade -c`, rehearse on `hastur` again, then run it against `carcosa`.

== Process / quality

* *No cross-role or full-stack testing.* Static tests and molecule both check a role in isolation, but the bugs that have cost the most here were interactions between roles: `iptables-restore` flushing fail2ban's chains, the `http` certificate bootstrap deadlocking against nginx, a certificate lineage name disagreeing with what three other roles read. Catching those needs `playbooks/site.yml` (see above) plus a run against a throwaway VM — a Hetzner instance created and destroyed per run costs about half a cent, so this can be automated even though production cannot. This is also the only way to close the gap that nothing currently checks whether a freshly provisioned host actually *serves* HTTPS, accepts mail or resolves DNS: molecule proves a role converges and is idempotent, and says nothing about whether the service works. Verification with `goss` or `testinfra`: ports listening, TLS chain valid, SMTP banner, and `fail2ban-client status <jail>` for the jails. See `doc/TESTING.adoc`.
* *Molecule covers six roles, and the rest are blocked for concrete reasons.* `doc/TESTING.adoc` holds the list and the per-role blocker; it is not repeated here, so that there is one place to update when a scenario is added. The short version is that `firewall` and `docker` want real netfilter and nested Docker, the service roles want real certificates and real cross-service communication, and `upgrade` reboots.
* A from-scratch provision has still never been proven end-to-end. `nyarlathotep` (the `testlab` group) now allows the roles to be run against real hardware, which is a large step up from molecule, but that machine was already part-configured before it was adopted, so a green run there does not prove a bare Ubuntu install would reach the same state. Proving it needs a reinstall first — `lab.sh reinstall-stage`/`reinstall-arm` exist for that but are **unverified and can strand the machine**, since it has no remote console. (`inventories/test/` is not this either: it is fake data for the tests and is never deployed.)
