= Project Status

This page summarizes what is currently implemented in the repository, as of the state of the `main` branch. It is a snapshot, not a guarantee — verify against the actual roles/playbooks before relying on details here for anything security-relevant.

== Scope

The repo configures a single physical/virtual server, host `carcosa`, serving the primary domain `drehtuer.net` and the secondary domain `drehtuer.de` (see `inventories/machines.yml`).

**The target OS is Ubuntu 24.04 LTS.** Moving to 26.04 is intended but gated by Ubuntu rather than by anything here: `do-release-upgrade` does not offer 24.04 -> 26.04 until the 26.04.1 point release. `doc/TESTING.adoc` records the rehearsal on a real guest, what it proved and what it did not. Check cheaply at any time with `ssh carcosa sudo do-release-upgrade -c`, which changes nothing. The `upgrade` role is ready for the day it opens, and the `testlab` guests run 24.04 so that the lab mirrors production rather than running ahead of it.

The inventory also holds a `testlab` group of disposable hosts used to run the roles against a real system before production sees them (see `doc/TESTING.adoc`): `testlab_vm` (`yuggoth`, a QEMU/KVM guest inside the dev container, the default) and `testlab_metal` (`nyarlathotep`, a LAN machine). Neither is part of the served infrastructure. All playbooks still target `hosts: all`, so `invoke run-playbook` requires `--hosts` — `production`, `testlab_vm`, `testlab_metal`, or a host name — rather than defaulting to every host. Anything environment-specific, credentials above all, lives in `group_vars/production/` or `group_vars/testlab/` rather than `group_vars/all/`, which is what keeps the production passwords off the test machine.

**Which domains this host serves is one list, not several.** `domain` and `domain_aliases` in `inventories/machines.yml` are the source; `http.domains` is derived from them as `[domain] + domain_aliases`, and the `mail` role reads the same two facts directly. Adding a domain there extends the certificate, every static vhost, the `cloud` and `spam` vhosts, Nextcloud's `trusted_domains` and Postfix's virtual aliases in one edit. Both domains therefore offer the same subdomains — `cloud.`, `mail.`, `spam.`, `status.`, `www.` — rather than the secondary being an alias of the primary.

**Both zones are managed here and both are live**, in `nsd.zones` — `drehtuer.net` since 2026-08-15, `drehtuer.de` since 2026-08-16 — each as a hidden primary with its own TSIG transfer key (see the `nsd` role below). `drehtuer.de` previously resolved to `78.46.107.174`, a different host; as of the cutover every name for it answers from `carcosa`, one certificate covers all 13 names across both domains, and Postfix accepts and delivers mail for both.

The cutover is worth recording, because the ordering is the whole lesson. Hetzner's console was switched to pull from here *before* `playbooks/nsd.yml` had been deployed, so for a while the zone existed nowhere: Hetzner had dropped its own copy, `carcosa` answered `REFUSED` because it had no such zone, and all three nameservers returned SERVFAIL. The symptom in the log was clean — `query: bad tsig (Bad Key) for key drehtuer.de.88.198.12.17.`, repeated every 40 seconds as the secondaries retried — and the fix was simply to run the playbook, after which the transfer completed at once. Deploy the zone first; the console change is what makes it visible, not what creates it.

Every name in `http.letsencrypt.subdomains` must resolve to this host for both domains before an `http` run: certbot validates each name over HTTP-01, and one failing challenge fails the whole certificate — including the renewal of names that were working. That constraint is now satisfied for both domains, but it is the reason the order above cannot be rearranged.

== Automation model

* Ansible roles under `roles/`, one per service/concern, each wired to a single matching playbook under `playbooks/`.
* No umbrella playbook exists yet — `playbooks/*.yml` are run individually. This is deliberate for now: it keeps each role easy to test in isolation while the configuration is still being built out, and a full from-scratch reinstall isn't needed yet since the target host already exists. An umbrella playbook remains useful future work once the individual roles have settled (see `doc/TODO.adoc`).
* `tasks.py` (python-invoke) wraps `ansible`/`ansible-playbook` with the correct inventory, vault, and become flags. Documented tasks: `ping`, `run-playbook`, `login`, `clean`, `install-hooks`, plus the lint tasks below and the test tasks in `doc/TESTING.adoc` (`test-static`, `test-molecule`, `test`, `check-drift`).
* Linting is enforced, not advisory: `yamllint --strict` (`.yamllint`), `ansible-lint` at its strictest `production` profile (`.ansible-lint`) and `ruff` check + format (`pyproject.toml`). The whole repo passes all three. They run via `invoke lint` (`--fix` applies what the tools can fix themselves), via the `.githooks/pre-commit` hook on staged files (enable once per clone with `invoke install-hooks`), and in GitHub Actions on pushes to `main` and pull requests (`.github/workflows/lint.yml`). ansible-lint reads `.yamllint` as well, so both YAML tools agree on style. CI has no vault password — it points `ANSIBLE_VAULT_PASSWORD_FILE` at a placeholder file, which is enough because linting never decrypts vaulted values.
* Testing has three automated layers plus a manual one: static tests (argument specs and template rendering against `inventories/test`, no host involved), molecule scenarios that converge a role in a systemd container and verify it is idempotent, and a local-only `invoke check-drift` that runs the real playbooks in `--check --diff` mode. Full-stack testing across roles is not built yet. See `doc/TESTING.adoc`.
* `inventories/test/` is a complete, deliberately fake and unencrypted inventory used only by the tests. It is what lets them run in CI, which has no vault password. Nothing is ever deployed from it.
* Secrets are stored one of three ways: inline `!vault |` values for individual fields in an otherwise-plain `inventories/**/*.yml` (the right choice when a file is mostly non-secret structure, e.g. `inventories/host_vars/carcosa/mail.yml`, so only the genuinely personal forward addresses are hidden); a whole `inventories/**/*.yml` file vault-encrypted top to bottom via `ansible-vault encrypt` (the right choice when a file is almost entirely secret anyway, e.g. `inventories/host_vars/carcosa/users.yml` - Ansible decrypts it transparently on load, same as an inline value, so nothing else has to change); or a whole encrypted file (`*.aes256`) decrypted at deploy time via `decrypt: true`, for content a role deploys as a file rather than reads as a variable (`roles/sshd/files/`, `roles/spam/files/nginx/`). The vault password lives in `vault/secret.txt`, referenced by `ansible.cfg` (`vault_password_file`), and is gitignored.
* Host SSH keys are pre-generated with `roles/sshd/scripts/generate_keys.sh` and vault-encrypted into `roles/sshd/files/`. The role copies them by content, so replacement is handled by `copy`'s own comparison rather than a separate checksum recorded in the inventory.
* Every role declares its inventory inputs in `meta/argument_specs.yml`, so a missing or misshapen variable fails at the start of the role with a named error instead of part-way through a run. Note that overriding a role's top-level dict in inventory *replaces* the role default rather than merging into it, so an override has to repeat every key the role needs.
* Every role's inventory input is a single top-level dict named after the role (e.g. `database:`, `mail:`), not a set of flat `<role>_<setting>` variables. This is what makes the previous bullet's argument-spec/replace-not-merge model work cleanly, and is deliberate enough to be exempted from `ansible-lint`'s `var-naming[no-role-prefix]` rule with a `# noqa` at each role's top-level `defaults/main.yml` key — that rule assumes the flat-variable convention and would otherwise ask for a redundant `database_database:`. Any *other* loose, unprefixed variable a role introduces (a `register:`, a `set_fact:`) is a real finding and should be fixed for real instead, as `roles/cloud`, `roles/database` and `roles/http` do.
* `inventories/group_vars/all/` vs `inventories/host_vars/<host>/` is chosen per file, not per convenience: a file goes in `host_vars/<host>/` when its content is inherently *about* that specific host — its connection details (`connection.yml`), the accounts that exist on it (`users.yml`), or content tied to its identity such as the domains/certificate it serves (`http.yml`) or the mailboxes it hosts (`mail.yml`). A file goes in `group_vars/all/` when it configures a *service* rather than a host's identity — settings that would be identical if the same service were deployed to another host too (package lists, firewall policy shape, database/cloud tuning, or a cross-role constant like `spam.milter_port`). With one production host this distinction has no observable effect, but it is the rule to follow as hosts are added, so a new file's placement should still follow it.

The `testlab` group is a deliberate exception: its `users.yml`, `http.yml` and `mail.yml` sit in `group_vars/testlab/` rather than per-host, because every test host is meant to be configured identically and only its connection details differ. Adding a third test host therefore costs one entry in `machines.yml` and one `connection.yml`.

== Services implemented

[cols="h,d", options="autowidth"]
|===
| Role | Implementation notes

| `system`
| Hostname, `/etc/hosts` and locales.

The hosts file is what the machine uses to answer questions about itself before DNS is consulted, so a stale entry misnames it locally however correct DNS is. Hetzner's install image leaves `Ubuntu-2404-noble-amd64-base` mapped to both public addresses, and nothing else rewrites the file, so it survived every later rename - `getent hosts 88.198.12.17` returned the image name until this role took the file over. It was also the reason an audit of what the DNS published briefly looked like an OS leak: the host's default resolver is systemd-resolved, which synthesises PTR answers out of `/etc/hosts`, so a local lookup disagreed with what the public nameservers actually served.

Each address is written only when the host really holds it, checked against `ansible_facts['all_ipv4_addresses']`/`ansible_facts['all_ipv6_addresses']` - which is why `playbooks/system.yml` gathers facts. The lab guests declare an `ip_v6` they do not have (it exists for the roles that need a value), and naming a machine by an address it cannot reach makes every local connection to itself try that address and wait for it to fail first. The inventory says what an address should be; the facts say what it is, and only the second belongs in a resolution table.

The fully qualified name comes first on each line, because `hostname -f` and most software wanting an FQDN take the first name after the address.

| `apt`
| Updates apt cache, installs a shared base package set (editors, shells, monitoring CLIs, unattended-upgrades, etc.).

| `users`
| Creates groups/users/passwords (all vault-encrypted) and passwordless-sudo for the `sudo` group; installs SSH `authorized_keys`. This role is the **single owner of supplementary group membership** — no other role may add an account to a group, since two roles writing the same field means neither can be authoritative. Membership and authorized keys are both managed authoritatively: dropping a group or a key from the inventory removes it from the host.

**One `authorized_keys` entry per user, listing every key that user may log in with.** The role loops `ansible.posix.authorized_key` over `users.authorized_keys` with `exclusive: true`, so a *second* entry for the same account does not add a key - it rewrites the file with only its own. Two entries leave the account reachable by the last key alone and report `changed` on every run. Put multiple keys in one entry, separated by a newline (a blank line inside the folded scalar, see `inventories/group_vars/testlab/users.yml`). This was found on the test lab; on a host without a console it would have been an unrecoverable lockout. The passwordless-sudo rule is load-bearing, because Ansible logs in unprivileged and escalates non-interactively.

| `sshd`
| Installs `openssh-server`; deploys vault-encrypted, per-host ed25519/RSA host keys and a shared screened `moduli` file; templates a hardened `sshd_config` that denies root login and password authentication, validated with `sshd -t` before it is installed. The config deliberately omits an `Include` of `sshd_config.d/`, so package drop-ins cannot weaken it.

| `firewall`
| `iptables`/`ip6tables` via `iptables-persistent`, default-deny INPUT/FORWARD, connection-rate limiting on rules marked `rate_limit`, and a data-driven allow-list (`firewall.rules.tcp`/`.udp` in `inventories/group_vars/all/firewall.yml`) currently opening TCP 22/25/53/80/443/587/993 and UDP 53. Both 53 rules are for the `nsd` role below, TCP because AXFR is TCP-only. Both address families render from one template, and each rules file is checked with `iptables-restore --test` before being installed.

Also manages the `DOCKER-USER` chain when `firewall.docker.enabled` is set. This matters because published container ports are DNATed and traverse `FORWARD`, never `INPUT` — without it, `docker run -p` is reachable from the internet regardless of the allow-list above. Container ports have to be opened explicitly in `firewall.docker.published`; everything else arriving on `firewall.docker.wan_interface` is dropped. That interface is fact-derived, which was worth confirming rather than trusting - a wrong name makes the drop match nothing, silently. It resolves to `enp0s31f6` on `carcosa`, which is the default route's interface and the real internet-facing NIC.

Restoring the rules flushes the whole `filter` table, taking Docker's own chains with it, so the role restarts both Docker and fail2ban afterwards — each only if that service is actually installed on the host. The fail2ban half of that turns out to be unnecessary on this host, which bans with the nftables action; see the `fail2ban` row above.

| `fail2ban`
| Installs fail2ban and templates `jail.local` from `fail2ban.jails`, covering `recidive`, `sshd`, `postfix`, `dovecot`, `nginx-http-auth`, `nginx-404`. Each jail sets `backend` to match how that service really logs: `systemd` for the journal (sshd, postfix), `auto` for the services this repo configures to write to files (dovecot via `roles/imap`, nginx via `roles/http`). Getting this wrong is silent — a journal-backed jail on a file-logging service simply never matches. Ships its own `filter.d/nginx-404.conf`, which the fail2ban package does not provide; verified against real traffic on the host with `fail2ban-regex` (1072 of 6830 log lines matched).


**The `postfix` jail needs a `journalmatch` override, because the packaged filter's can never match on Debian or Ubuntu.** `/etc/fail2ban/filter.d/postfix.conf` ships `_SYSTEMD_UNIT=postfix.service`, but both distributions run Postfix as the instantiated template unit `postfix@-.service`; `postfix.service` is a wrapper that starts it and then says nothing. Measured on the host, the wrapper emitted 14 journal lines in a fortnight and zero authentication failures, against 26186 lines and 399 failures for `postfix@-.service` — so the jail read a unit with nothing in it and reported `Total failed: 0` on a host with hundreds of real failures. `fail2ban-regex` puts it beyond doubt: 0 lines and 0 matched with the packaged value, 281429 lines and 9897 matched with the override. It is set as a `journalmatch` key in that jail's `options`, which the template already passes through generically, so no template change was needed.

Two things about that are worth knowing. fail2ban *combines* the jail's `journalmatch` with the filter's rather than replacing it, and `+` is journalctl's OR — so `fail2ban-client status postfix` reports the effective match as `_SYSTEMD_UNIT=postfix.service + _SYSTEMD_UNIT=postfix@-.service`, which reads both units. That is harmless here, the wrapper contributing nothing, but it means an override of this kind widens rather than substitutes. And enabling a jail that had never matched makes it sweep the journal backlog it can now see: the reload banned four addresses at once, all for activity earlier the same day rather than anything current.

That sweep also caught the administrator's own address, which is the practical trap. Manual SMTP testing from a workstation — relay probes, deliberately bad sender domains — is exactly what the `postfix` filter in `mode = normal` counts, so testing the mail server from home earns a ban on `smtp,submission` once this jail works. There is no `ignoreip` in `jail.local`; adding one for the administrator's networks is the obvious answer if this becomes a nuisance, at the cost of exempting those addresses from every jail.
The installed fail2ban bans with the **nftables** action, not the iptables one, which was an open question for a while: it means its chains live in the `nft` ruleset and are *not* taken out by the `iptables-restore` flush in the `firewall` role. That role restarts fail2ban after a rules change anyway. Harmless, and cheaper to leave in place than to make conditional on a ban action the host could change under it.

**Restarting fail2ban used to break the web UI, and the cause was systemd rather than either of them.** `fail2ban.service` declares `RuntimeDirectory=fail2ban`, so systemd deletes and recreates `/run/fail2ban` on every stop - a different inode each time. That is invisible until something bind-mounts the directory, and `roles/fail2ban_ui` does exactly that to reach the control socket. A container keeps the mount it was given, so after any restart it holds the old, unlinked directory: it sees an *empty directory* rather than an error, and the UI reports it cannot reach the socket until the container is recreated.

Found on 2026-08-16, where the trigger was this repo's own `Restart fail2ban` handler in `roles/firewall` firing after a rules change - but a package upgrade would do it just as well, so removing that one trigger would not have been a fix. The role now ships a `RuntimeDirectoryPreserve=yes` drop-in, which keeps the directory across a stop so the socket is simply recreated inside the one already mounted. Proven by restarting fail2ban and watching the inode stay put on both sides of the mount. The setting lives in `roles/fail2ban` rather than in the UI's role because this one owns `fail2ban.service`.

**The fail2ban UI and `roles/fail2ban` both write `jail.local`, and the role wins.** The UI's Global Settings are written into that file's `[DEFAULT]` section, so anything changed through the web interface is reverted by the next `playbooks/fail2ban.yml` run. Change jails in `fail2ban.jails` and deploy; treat the UI as read-plus-ban rather than as a configuration editor. Starting the container does not itself touch the file — verified after deploying, `jail.local`'s mtime was unchanged and the fail2ban role reported no drift.
+
A way out exists and was deliberately *not* taken, on 2026-08-16 — recorded here so the research is not repeated. fail2ban reads its configuration in a fixed order, from `configreader.py`: `jail.conf`, then `jail.d/*.conf` sorted, then `jail.local`, then `jail.d/*.local` sorted, with later files overriding earlier ones. `jail.d/*.local` therefore outranks `jail.local`. Pointing this role's template at `/etc/fail2ban/jail.d/zz-ansible.local` (plus `state: absent` on the old `jail.local`, and the `zz-` prefix to stay last in a sorted glob) would make Ansible win every key it sets, immediately and deterministically, while leaving the UI usable for anything the role does not set. The template itself would not change — only the `dest`.
+
It was left alone because it trades one silent failure for another: today a UI edit applies and is then reverted at the next playbook run, whereas afterwards it would never apply at all, and the UI would still *display* its own `jail.local` values rather than the effective ones. Neither tells the operator anything. Going the other way is worse and should not be considered: `JAIL_AUTOMIGRATION=true` is the only setting upstream offers that moves the UI's writes, it is documented as "Experimental migration from a monolithic `jail.local` to `jail.d/*.local`. On production systems, migrate manually instead", and it would put the UI's file *above* Ansible's — inverting which system is authoritative. There is no read-only mode and no other write restriction in the image's configuration reference.
+
Worth re-checking when the UI is next upgraded: an upstream option to target a specific file, or a genuine read-only mode, would settle this properly and is the preferred outcome over either workaround.

**`nginx-http-auth` is confirmed to match, as of 2026-08-16.** It had never fired once, which was consistent with nobody having failed basic auth rather than with a broken jail — nginx logs an error only when credentials are actually *submitted*, not for the 401 challenge itself, so an untouched counter proved nothing either way. Failed logins against the `f2b.<domain>` realm took it from 0 to 5 `Total failed`, so the filter and its `logpath` are right. Note what this does not yet show: `maxretry = 5` within `findtime = 10m` was never reached inside one window, so the ban *action* here remains untested — a much lower bar than the filter, but not the same claim. Worth knowing before testing it deliberately: a ban is 1h, and `recidive` escalates a repeated one to 1w against `port = all`, which locks the address out of SSH as well as HTTPS.

| `time`
| `ntpsec` with Hetzner NTP servers, hardware clock in UTC, timezone `Europe/Berlin`.

| `cron`
| Installs and enables the `cron` service (other roles add their own cron jobs, e.g. Nextcloud background jobs).

| `dns`
| Installs `unbound` + `unbound-anchor` as a **local, loopback-only DNS-cache/validating resolver** (`interface 127.0.0.1`/`::1`, all other sources refused) and configures `systemd-resolved`. Authoritative service is a separate role — see `nsd` below — and the two coexist deliberately rather than one replacing the other: unbound answers recursively on loopback, NSD answers authoritatively on the public addresses, and each names its addresses explicitly so they cannot collide.

**Cache and statistics.** `prefetch`/`prefetch-key` renew popular entries shortly before they expire rather than making the next client wait for the recursion, and the message/rrset caches are raised from the 4 MB defaults. Runtime statistics are available through `unbound-control stats`, which is deliberately bound to a *unix socket* (`/run/unbound.ctl`, `root:unbound`) rather than the default TCP port 8953: a socket opens no network port at all, so there is nothing for an external address to reach even if the access-control rules were later loosened, and it removes the need for the control certificates `unbound-control-setup` would otherwise generate. Verified on a live host - `ss`, `lsof` and a direct connection attempt all agree that unbound owns only `127.0.0.1:53` and `[::1]:53`.

Note that `systemd-resolved` is set to `DNSSEC=allow-downgrade`, not `yes`: unbound has already validated every answer before resolved sees it, and validating twice adds nothing while making resolved's weaker implementation a failure source of its own. Queries still reach unbound only - stopping it breaks system resolution rather than falling back to the DHCP-provided server, which was checked rather than assumed.


`unbound-resolvconf.service` is masked. The package ships it to point the system's `resolv.conf` at unbound through resolvconf, and it cannot work on this host: it attaches a DNS server to the link `lo`, which systemd-resolved refuses outright ("Link lo is loopback device"). The wiring it exists to do is done by the role's `resolved.conf` instead, which points systemd-resolved at `127.0.0.1`. Masked rather than disabled, since it is `WantedBy` unbound.service and a package upgrade re-enabling it would quietly bring the failure back; a masked `Wants` is skipped without failing the parent. The failure systemd had already recorded needs clearing separately - masking a unit leaves it listed as masked *and* failed - which the role does, guarded so a converged host reports no change.

This mattered out of proportion to the symptom: it was the only failed unit on the host, so `systemctl list-units --state=failed` - the cheapest health check available - never read clean, and any real failure would have had to be spotted among the noise.
| `nsd`
| Authoritative DNS for the zones in `nsd.zones` — `drehtuer.net` and `drehtuer.de` — alongside the `dns` role's unbound rather than instead of it: NSD binds the public addresses, unbound stays on loopback, and each names its addresses explicitly so they cannot collide.

**No task in this role loops over the zone dicts themselves, and that is deliberate.** Ansible prints the whole `item` when a looped task fails, and a zone carries its `tsig.secret` — so looping over `nsd.zones` puts the transfer key for every zone into the output of any failure. That is not hypothetical: it happened, and both secrets had to be rotated as a result. Tasks loop over `nsd.zones | map(attribute='name')` and look the zone up in `vars` instead. Keep it that way when adding one.

**Rotating a TSIG secret is a two-ended change with no rollover.** The key is symmetric and Hetzner holds the other copy, so changing it here alone stops transfers until their console is updated; the secondaries keep serving their existing copy meanwhile, so it is not an outage but nothing propagates. Two things learned doing it on 2026-08-16 and worth not rediscovering: a green `nsd.yml` run does *not* prove transfers work, because changing `tsig.conf` alone does not move the serial and the propagation check therefore has nothing to detect — force a serial bump to test it. And Hetzner answers a NOTIFY signed with a key it does not recognise with `SERVER NOT AUTHORITATIVE FOR ZONE` rather than any TSIG error, which is the signal that one zone's secret did not take.

**The role verifies serials rather than trusting them.** Two failures hide here and both are silent, because this host answers correctly either way while the world keeps a stale zone. A serial that never moved: edit a record, forget `nsd.zones[].serial`, and the file is written, `nsd-checkzone` passes and nsd reloads with the new data, but the secondaries compare serials, see no increase and never ask for the zone. That is only detectable by comparing what the server *was* answering against what the inventory now says, so the role reads the live serial before writing anything and fails if a changed zone did not bring a higher one. A serial that moved and never arrived: a refused transfer, a TSIG key that stopped matching, a NOTIFY that never landed — so after reloading, the role asks every nameserver in each zone's own NS records (the servers the world actually queries, rather than the transfer ACL) and fails if one does not catch up, retrying because a transfer takes a moment. All three checks are read-only and carry `check_mode: false`, so `invoke check-drift` catches a forgotten bump before it is deployed.

**Both zones have been DNSSEC-signed since 2026-08-16, and nothing validates them yet — deliberately.** NSD cannot sign; `nsd-sign-zone` (deployed by this role) runs `dnssec-signzone` over the generated zone file and nsd serves the `.signed` result. A signed zone with no DS record in its parent is treated by every validator exactly as an unsigned one, which is what makes this half safe to deploy and check at leisure. Publishing the DS at the registrar is the separate step that turns validation on, and it is the one that cannot be undone quickly — see `doc/TODO.adoc`.

Keys are ECDSAP256SHA256, one KSK and one ZSK per zone, generated by `roles/nsd/scripts/generate_dnssec_keys.sh` and vault-encrypted into `files/dnssec/` — the same stance `roles/sshd` takes with host keys, and for a sharper reason: the DS record in the parent points at the KSK, so a host rebuilt without it would need a new DS published and propagated, during which the zone is not unsigned but *bogus*. The split exists so that a ZSK roll never involves the registrar.

**The serial is computed by the signing script, and every obvious way of doing that is wrong.** `dnssec-signzone`'s `-N` flag looks like it handles this and does not: every mode derives the output serial from the *input* file, which is generated from the inventory and does not change between re-signings. So `increment` yields source+1 every time and `date` yields today's YYYYMMDDNN every time — sign three times, get one number three times, measured rather than assumed. `unixtime` is worse still, because this repo's YYYYMMDDNN serials (around 2026081504) far exceed a 2026 unix timestamp (around 1786000000), so it would *lower* the serial and dnssec-signzone quietly falls back to incrementing. A serial that does not rise is the one failure that matters: the secondaries never fetch the refreshed signatures and their copies expire into bogus about a month later while this host looks healthy. The script therefore reads the serial in effect, adds one (or jumps to today's date serial when that is ahead) and signs with `-N keep`. `nsd.zones[].serial` is consequently the serial of the *unsigned source* only.

**Re-signing weekly is load-bearing, not housekeeping.** Signatures are valid 30 days and `nsd-resign.timer` re-signs every seven. If it ever stops, the zones do not degrade to unsigned — they become bogus, and validating resolvers refuse every answer. Note the scope of that: it only bites once a DS exists in the parent. While the zones are signed but undelegated, as they are now, resolvers never consult the RRSIGs at all and expiry is inert. It becomes an outage risk on the day the DS is published, not before.

**A systemd timer rather than cron, for `Persistent=true`.** Cron silently skips a run whose moment passed while the host was down, and `roles/upgrade` exists to reboot this machine; the timer catches up on the next boot instead. The cron file it replaced is actively removed rather than left alongside — it would sign a second time each week, and worse, keep working when the timer was broken, hiding the very failure the timer's mail exists to report. The signing script is silent unless run from a terminal, so mail from the timer means something is wrong rather than arriving fifty-two times a year regardless.

**Scheduling proves a job started, not that it worked**, so the role also checks what is actually being served: it reads the RRSIG expiry from the SOA's signature and fails below `nsd.dnssec.min_signature_days`. A missing key, a full disk or a broken `nsd-control` all fail quietly otherwise, and the first visible symptom would arrive weeks later. Confirmed non-vacuous by demanding more days than exist, which fails and reports the real figure.

**The zone list is deliberately not derived from `domain`/`domain_aliases`**, unlike `http.domains` and everything downstream of it. Those say which domains this host *serves*; `nsd.zones` says which zones it is *authoritative* for, and a domain can perfectly well be served here while its DNS stays somewhere else — which is exactly what `drehtuer.de` was until the zone below was written. A zone also needs hand-written records, its own serial and its own transfer key, none of which follow from a domain name.

**One TSIG key per zone, not one per server.** Hetzner leaves no choice about the key *name* — its console derives it as `<zone>.<primary-ip>.` — so two zones cannot share one even if they shared a secret. The secrets are kept separate as well, so rotating or replacing one domain's key never touches the other's and a leak costs one zone. `nsd.zones[].tsig` therefore holds `name`/`algorithm`/`secret`; the role renders all of them into a single `nsd.conf.d/tsig.conf`, deduplicated by name because NSD refuses a config that defines the same key twice. The static tests assert that the number of distinct key names rendered equals the number of zones, which is what would catch a template regressing to one shared key.

**This cannot become an open resolver.** NSD is authoritative-only software - it contains no recursion code at all, so a query for a name outside its zones is answered `REFUSED` and the recursion-available flag is never set. That is the reason to use it here rather than BIND, which *can* recurse and merely has to be told not to. Verified on the live host: `REFUSED` for a foreign name on the public address, no `ra` flag, and the resolver unreachable from off-host. Response rate limiting is on as well, since an authoritative server can still be abused as a reflector even though it cannot resolve.

**Hidden primary.** The zone's NS records still point at Hetzner's nameservers, which pull the zone by AXFR; the world queries them, not this host, so an outage here stops updates propagating rather than taking the zone down. `provide-xfr` names exactly Hetzner's six addresses and requires a TSIG key from each. NOTIFY goes to a deliberately narrower list - the same three servers, but their IPv4 addresses only, because Hetzner answers a NOTIFY arriving from this host's IPv6 address with REFUSED whatever key signs it. That was established by probing each candidate key name against each address rather than guessed at: an unknown key is answered NOTAUTH, while the working key over IPv6 is answered REFUSED, so the key verifies and the notify is declined on policy. Nothing is lost, since those are the same three servers; what it removes is eighteen error lines per zone change, which is how a log stops being worth reading. NOTIFY is otherwise sent so they transfer promptly instead of waiting out the SOA refresh. AXFR is TCP-only, which is why the firewall opens TCP/53 as well as UDP/53.

**unbound could not do this job.** Its `auth-zone` only ever *downloads* a zone - "where to download a copy of the zone from, with AXFR and IXFR" - and has no way to answer a transfer request, so a secondary asking it for AXFR gets nothing.

**Transfers are authenticated with TSIG**, a shared secret and an HMAC over the DNS message (RFC 8945). It lets the secondary verify that the zone it received really came from this host and was not altered in transit, and lets this host refuse a transfer to anyone who cannot prove they hold the same secret - source-address restriction alone is defeated by a spoofed packet and tells the secondary nothing about integrity. Hetzner accepts `hmac-md5`, `hmac-sha1` and `hmac-sha256`; only the last is unbroken.

The key *name* is not free to choose. Hetzner's console takes only the algorithm and the secret and derives the name itself as `<zone>.<primary-ip>.`, so each zone's `tsig.name` has to be written out to match. Getting it wrong is not a soft failure: NSD answers BADKEY, no transfer ever succeeds, and once the secondaries' copy passes the SOA expire time they stop answering for the zone at all and the domain goes dark - which is exactly what happened here, with the name guessed as `hetzner-secondary`. The name a secondary actually presents is in `journalctl -u nsd | grep tsig`, so check it against a real transfer attempt rather than assuming. The secret lives in its own included file rather than in `nsd.conf`, so that a `--diff` from the drift check does not print it, and the task writing it sets `no_log`.

TSIG is *not* DNSSEC and neither substitutes for the other. TSIG authenticates the hop between two servers with a shared secret and leaves nothing in the zone; DNSSEC signs the zone data with public-key cryptography so any validating resolver can check an individual answer. A TSIG-protected transfer of an unsigned zone is still unverifiable to the outside world. (DANE is a third thing again - TLS certificate constraints published as TLSA records, riding on DNSSEC.)

**Do not add a catch-all `provide-xfr: 0.0.0.0/0 BLOCKED`.** It reads as harmless belt and braces and silently breaks every transfer: per `nsd.conf(5)`, "BLOCKED supersedes other entries, other entries are scanned for a match afterwards", so it blocks the listed secondaries too. This was in the role's first version and was caught only because the lab was changed to point `nsd.secondaries` at the test host itself, which made a *successful* transfer testable - pointed at an unreachable documentation address, every attempt was refused on source address and a broken ACL looked exactly like a working one. NSD default-denies transfers on its own; that was verified separately.

The serial in `nsd.zones[].serial` must be increased by hand whenever that zone's records change: secondaries compare serials and keep their old copy if it does not rise. It is an explicit value rather than a timestamp so re-running the role without a content change stays idempotent. Note that the serials are per zone — bumping `drehtuer.net` does nothing for `drehtuer.de`.

Neither zone is DNSSEC-signed and neither has a DS record in its parent, checked against the `.net` and `.de` delegations on 2026-08-16. That is what made moving `drehtuer.de`'s primary here safe to do without signing it first: there is no chain of trust to break. It also means the open DNSSEC question in `doc/TODO.adoc` now covers two zones.

| `database`
| MariaDB (root user/password vault-encrypted, idempotent via a `/root/.mysql_root_password_set` marker file) and Redis (16 logical DBs), both bound to loopback only and neither reachable from off-host.

**Both bindings are owned by this repo**, which was not always true: MariaDB used to be loopback-only purely because Ubuntu ships it that way in the package-owned `50-server.cnf`. Correct, but unmanaged - a package upgrade rewriting that file could have exposed the server with nothing here to prevent or notice it. It is now set from `database.mysql.bind_address` through a `conf.d` drop-in, deliberately *not* by replacing the packaged file: that is precisely how Redis lost its `dir` setting and started refusing every write. Redis is healthy again on `carcosa` - `dir` is `/var/lib/redis` and a write returns `OK` rather than `MISCONF`, which matters because that failure was invisible to `PING` and silently broke both RSpamd's Bayes learning and Nextcloud's file locking.

Exposure is defence in depth rather than one setting: both listen on loopback only, the firewall opens neither 3306 nor 6379, and every MariaDB account is scoped to `localhost`/`127.0.0.1` - the role's first-run handlers remove the anonymous users, drop remote `root` (`%` and `::1`) and delete the `test` database. Redis has `protected-mode` on and no password, which is deliberate: it relies on the loopback binding, so exposing it would need both a binding change and a firewall change.

| `docker`
| Installs Docker Engine + Buildx + Compose v2, enables `docker`/`containerd`, and writes `/etc/docker/daemon.json`: `json-file` logging capped at 10 MB × 3 (the driver rotates nothing by default, so container logs otherwise grow until the disk fills) and `live-restore`, which keeps containers up when the daemon restarts — including the restart the `firewall` role triggers on every rules change. Docker group access is granted through the `users` role, not here. Its first and so far only consumer is `fail2ban_ui` below, which runs a Compose stack — the groundwork paid off in that no bootstrap step was needed to add it. | `http`
| nginx + certbot + php-fpm. Builds a `conf-server`/`sites-available`/`sites-enabled`/`locations-available`/`locations-enabled` layout, generates a 4096-bit DH param, and applies hardened SSL/security headers (HSTS, CSP, X-Frame-Options, etc.) from `conf-server/security.conf`.

Note how nginx inherits `add_header`: a `location` inherits the enclosing level's headers only while it declares *none* of its own, and declaring one drops all of them. So any block that adds a header — `roles/cloud`'s `/nextcloud` location and its static-asset blocks — has to repeat the security headers, HSTS included, rather than relying on the vhost's. Getting this wrong is invisible in `nginx -t`; it shows up only as a missing header on the response.

HSTS is `max-age=31536000; includeSubDomains`, repeated verbatim in all five places that send it. One year is what a preload-list submission would require, but the `preload` token is **deliberately omitted**: it is the consent signal `hstspreload.org` checks for, and delisting a domain again takes months of browser releases to reach users. If the token is ever added, every copy has to gain it at once — a domain sending it inconsistently across vhosts is the kind of thing that only surfaces at submission time.

**Multi-domain.** `http.domains` lists every domain this host serves, derived from the host facts as described under <<Scope>>. The certificate and all static vhosts are built from it, so adding a domain is a one-line inventory change. Static vhosts are declared in `http.sites` and rendered from a single template; `server_name` is the cross product of the domains and each site's subdomains. Application roles (`cloud`, `spam`) add their own vhost rather than appearing there, and both of them fan out over `http.domains` the same way.

**Certificate.** One certificate covers every domain, each `http.letsencrypt.subdomains` entry per domain, and the host FQDN — a SAN list rather than a wildcard. A wildcard would need DNS-01 validation, i.e. a Hetzner DNS API credential and a certbot plugin that is not packaged for Ubuntu, and `*.example.com` does not cover `example.com` anyway; at 11 names against Let's Encrypt's cap of 100 there is nothing to gain. Its lineage name is pinned to `http.letsencrypt.cert_name` (the FQDN) rather than being derived from the first `-d`, which is what other roles read out of `/etc/letsencrypt/live/<name>/` — and what lets the `-d` list be sorted without moving the lineage. Renewal is scheduled by `certbot.timer`, and a deploy hook reloads nginx/postfix/dovecot after a renewal actually happens. The pinning was worth checking on the host, since an older certbot would have derived the lineage from the first `-d` and left two lineages renewing in parallel: `certbot certificates` reports exactly one, named `carcosa.drehtuer.net`, carrying the seven `drehtuer.net` names.

**Issuance is driven by the names on the certificate, not by its existence.** The role reads the SANs off `/etc/letsencrypt/live/<name>/cert.pem` with `openssl` and runs `certbot certonly --expand` only when that set differs from the one the inventory asks for. A `creates:` guard on the lineage was the earlier approach and was actively wrong: it made adding a domain render vhosts for a name the certificate did not cover, serve them with a mismatched certificate, and still report success.

**Bootstrap order matters and is encoded in the task order.** The port-80 vhost serves the ACME challenge directly instead of redirecting it, goes up before certbot runs, and the TLS vhosts are written only afterwards — otherwise nginx cannot start without a certificate that cannot be issued without nginx. `nginx -t` runs before the port-80 server is started and again at the end of the role.

**PHP.** The version is detected at run time and used for the service name, socket and config paths, rather than being hardcoded — the `upgrade` role changes it.

**OCSP stapling was configured and never worked, and the directives are gone.** `ssl_stapling` and `ssl_stapling_verify` were set, but Let's Encrypt has retired OCSP and the issued certificate carries no responder URI - so nginx had nothing to fetch and nothing was ever stapled, confirmed with `openssl s_client -status` reporting "no response sent". They were removed on 2026-08-16 rather than left: they did no harm, but they read as a working security feature to anyone auditing the file, which is worse than their absence. The `resolver` line stays - it was added for stapling but is not specific to it, and nginx needs one to resolve any name it looks up at run time.

| `cloud`
| Installs Nextcloud PHP dependencies, creates its MariaDB database/user, and installs a **pinned** Nextcloud release (`cloud.nextcloud.version`, verified against `cloud.nextcloud.checksum`) to `cloud.nextcloud.path`. Adds its own PHP-FPM pool — named `nextcloud`, not `www`, on its own socket — plus the matching nginx upstream, a `cloud.<domain>` vhost for every configured domain, and the path-based `/nextcloud` location. PHP tuning is a `conf.d` drop-in rather than edits to the package-owned `php.ini`, deployed to the FPM *and* the CLI SAPI because the background job and `occ` run under the latter. Adds the Nextcloud background job and a PNG-iCCP-cleanup cron job. Installs `ocrmypdf` plus the Tesseract training data for each `cloud.ocr.languages` entry, which Nextcloud looks for on `$PATH`.

**Caching.** `memcache.local` (APCu), `memcache.distributed` and `memcache.locking` (both the shared Redis from the `database` role, on `cloud.redis.dbindex` so it does not share a logical database with RSpamd) are configured through `config/cache.config.php`. That is an *additional* config file: Nextcloud reads every `config/*.config.php` after `config.php` and only ever writes back to `config.php`, so the role can own these settings without owning the file the installer writes. `apc.enable_cli` is set, since APCu is off in the CLI SAPI by default and the background job would otherwise run without the local cache.

Install only, never upgrade: the download is gated on `version.php` being absent, because unpacking a newer release over a live installation without `occ upgrade` breaks it. Bumping the pinned version therefore does *not* upgrade an existing host.

**Trusted domains.** Nextcloud rejects any request whose `Host` it does not recognise, so `config/domains.config.php` — the same drop-in mechanism as the cache settings — lists every name the nginx configuration actually serves it under: `cloud.<domain>` for each domain, plus each `http.sites` entry that pulls in `locations-enabled/*.conf` and therefore exposes the path-based `/nextcloud`. Both are derived, so a new domain or site is picked up automatically. It also sets `overwrite.cli.url`, which the background job needs because a CLI run has no request to derive a host from. Note that this key *replaces* `trusted_domains` from `config.php` rather than merging with it — a name added there by hand stops working until it is in the inventory.

Does **not** run the Nextcloud web/`occ` installer (admin account, `config.php`) — that step is manual, and on `carcosa` it has been done by hand: `occ status` reports `installed: true` on 34.0.3, with all three `config/*.php` files in place. So the gap is only felt on the *next* host built from this repo, which is why it stays in `doc/TODO.adoc` rather than being closed.

**A weekly cron job was rewriting every PNG in the installation, and it has been removed.** It ran `find /var/www/nextcloud -type f -name '*.png' -exec mogrify -strip {} +` as `www-data` to silence libpng's "known incorrect sRGB profile" warning — cosmetic log noise. What it actually did, found on 2026-08-16 when Nextcloud reported code integrity failures:

* **Broke the integrity check.** `mogrify -strip` re-encodes the file, so every signed PNG stopped matching its hash: 48 core files plus assets in two apps. Every damaged file carried an mtime of `03:00:0x`, exactly the job's schedule, which is what identified it.
* **Destroyed at least one file.** `apps/podcast/dist/screenshot2.png` was left at zero bytes — its recorded hash is the SHA-512 of an empty string. So this was not only re-encoding but occasionally truncating.
* **Was rewriting user uploads.** The data directory lives *inside* the installation directory here, so 2163 of the 2480 PNGs it touched weekly were under `data/` and 425 were files a user had uploaded. Verified on a copy that `mogrify -strip` does alter them. None currently carry an `03:00` mtime, so no user file is known to have been damaged — but that is luck rather than design, and the job would have got to them.

Core was repaired by re-extracting the pinned release over the installation, which is safe precisely because the tarball contains no `data/` or `config/` — the same property the upgrade path relies on. `files_archive` was repaired from its release tarball. `podcast` could not be: its app-store download URL is a CI artifact that now 404s, so the version cannot be fetched again at all.

The lesson worth keeping is narrower than "do not run mogrify". A scheduled job given the *installation root* as its scope will reach application code and user data alike, and neither belongs to it. Anything of this kind needs a path that names what it is actually for.

**Client Push (`notify_push`) replaces polling.** Without it every connected client asks Nextcloud every 30 seconds whether anything changed — most of the idle load a quiet instance carries, and the reason a Talk call can ring up to half a minute late. With it, clients hold one WebSocket open and Nextcloud pushes. The app ships the daemon as a prebuilt binary per architecture, so this is an app install and a systemd unit rather than a build; the unit reads Nextcloud's own `config.php` for its database and Redis details, so there is nothing to keep in step by hand.

It is bound to loopback and reached at `/push/` on the Nextcloud vhost — that exact path, because `occ notify_push:setup` both expects it and self-tests it. That self-test is the useful part: it checks Redis, the database, the connection back to Nextcloud, the trusted-proxy chain and version agreement, and refuses to save a configuration that does not work.

**It needs `trusted_proxies`, and the self-test is how you find that out.** The daemon calls back into Nextcloud forwarding the real client address in `X-Forwarded-For`, and Nextcloud ignores that header unless the sender is trusted — so without it every pushed event is attributed to the push server. `config/proxy.config.php` lists both loopback addresses and both of this host's public ones, because the daemon reaches Nextcloud through the public name rather than over loopback. Note this only widens which senders may *claim* a client address, and every address listed is this host; nginx talks to PHP over FastCGI rather than HTTP, so ordinary web requests never took that path.

**The installer and the upgrade are both automated, and the upgrade is the delicate one.** A host with no `config/config.php` gets `occ maintenance:install` run for it — the last step that was still done by hand, and so the last thing standing between this repo and a rebuild. A host whose installed `versionstring` differs from `cloud.nextcloud.version` gets upgraded: maintenance mode, database dump, extract, `occ upgrade`, then the `db:add-missing-*` commands behind the admin overview's warnings. Both are no-ops otherwise, which is why deploying this to `carcosa` changed nothing.

**Why the upgrade extracts over the top and deletes nothing.** The data directory sits *inside* the installation directory here (`/var/www/nextcloud/data`, 104 GB), and the release tarball contains no `data/` or `config/` — so unpacking over the old release cannot touch either. The tidier scheme, deleting whatever the tarball does not contain, is how the official updater removes stale files; here it would delete every user's data. Stale files from the previous release are left behind instead. They are inert, and with no backup strategy in this repo yet (see `doc/TODO.adoc`) that is the right trade.

**The database dump is the only thing that makes an upgrade reversible.** Files can be restored by re-extracting a tarball; a schema migration cannot. It is taken after maintenance mode, so nothing is writing during it, and named for the transition (`nextcloud-34.0.2-to-34.0.3.sql.gz`) rather than a timestamp. It runs as Nextcloud's own database account rather than root — least privilege, but also necessary: `root@localhost` authenticates by `unix_socket`, so handing `mariadb-dump` a root password fails with *"Access denied (1698)"* even though every other task in this role connects as root happily, because those go through the socket instead of forcing a password login.

**Turning maintenance mode off is in an `always` block.** An upgrade that fails is recoverable; one that fails *and* leaves the instance behind a maintenance page needs someone at a terminal. Proven rather than assumed — the dump failure above happened during testing and maintenance mode came off anyway.

**A multi-major jump is refused before anything is touched.** Nextcloud upgrades one major version at a time and refuses more, but it refuses *after* the files have been replaced, leaving the installation unusable until someone restores the old release by hand.

All of it was proven on the lab rather than on `carcosa`: wiped, installed 34.0.2 from scratch, then upgraded to 34.0.3 and re-run to confirm it settles at `changed=0`.

**Nextcloud `trusted_domains` is role-owned and replaces what is in `config.php`.** The key in `config/domains.config.php` overrides the array the installer wrote rather than merging with it, so a name added to `config.php` by hand stops working on the next `playbooks/cloud.yml` run. Compare `occ config:system:get trusted_domains` against the rendered file before deploying a change to the domain list.

**Nextcloud rotates its own log, because nothing else does.** It writes into the *data* directory rather than `/var/log`, so no packaged logrotate config covers it, and upstream's `log_rotate_size` defaults to unset — which means zero, disabling rotation rather than choosing a default. On `carcosa` that went unnoticed for over a year: 94 MB in one file, oldest entry 2025-08-03. `cloud.nextcloud.log_rotate_size` now sets it, through a `config/*.config.php` drop-in like the cache and domain settings beside it.

Nextcloud's own rotation was chosen over a logrotate drop-in: it needs no coordination over a file the web server owns, and it is what upstream documents. The trade is retention — Nextcloud keeps exactly *one* previous file, so the ceiling is two generations, about two years at this host's rate. Switch to logrotate if arbitrary retention ever matters more.

Two things worth knowing. Rotation is lazy: the size is checked as a line is written, so an oversized log is renamed on the next log entry rather than on a schedule. And because a `*.config.php` drop-in is read *after* `config.php`, this key overrides anything `occ config:system:set log_rotate_size` writes — the same role-owns-it caveat that already applies to `trusted_domains`.

Verified by lowering the threshold on the host until it fired, rather than by trusting the setting: the 94 MB file was renamed to `nextcloud.log.1` and a fresh one created, after which the playbook restored the real value. Worth noting for anyone reading that log — roughly 90% of it was a single repeated warning, `Capabilities of OCA\Theming\Capabilities took 0.67 seconds to generate`, which is a performance complaint rather than a fault and is a separate question from rotating it.

| `mail`
| Postfix: opportunistic TLS outbound (`smtp_tls_security_level = may` - try STARTTLS with every peer, fall back to cleartext for the ones that do not offer it, which is the only workable policy for a public MX), TLS-only submission using the Let's Encrypt cert, SASL auth via Dovecot, alias + virtual-alias maps (vault-encrypted where they contain personal data), mail routed to Dovecot over LMTP, and RSpamd wired in as a milter on `mail.spam.milter_port` (`milter_default_action = accept`, i.e. fails open if RSpamd is unreachable). The milter connection works, on the test host and on `carcosa` both: Postfix has `smtpd_milters = inet:127.0.0.1:11332`, RSpamd's proxy worker is listening there, there are no connection errors, and RSpamd's verdict headers are present on delivered mail. This sat open as a suspected breakage for a long time and turned out to be nothing - the `connect to Milter service` errors that started it predated the `spam` role ever being deployed. `milter_default_action = accept` still means mail flows if RSpamd is ever unreachable, so a silent failure degrades to *unfiltered* rather than *undelivered* - worth knowing when judging whether filtering is actually running.

**Every domain this host serves accepts mail, and every account has one inbox across all of them.** `virtual_mailbox_domains` is rendered as `[domain] + domain_aliases` plus `$myhostname`, so `drehtuer.de` is a first-class mail domain rather than a decorative one.

Before that it held only `$mydomain`, and a secondary domain was in **no address class at all** — which is not what this document previously claimed. The old note said acceptance came for free because the domain appears on the left of `virtual_alias_maps` and Postfix defaults `virtual_alias_domains` to `$virtual_alias_maps`. That is wrong: pointed at a map, `virtual_alias_domains` looks the *bare domain* up as a key, and `/etc/valiases` is keyed on full addresses, so `postmap -q drehtuer.de` misses and the domain never entered that class. The aliased addresses still worked, because alias rewriting runs for every recipient whatever class it is in — which is precisely what hid the gap.

The consequence was worse than a refusal. An ordinary account at the secondary domain matched nothing, fell through to the default class, and Postfix tried to deliver it *off-host* — `relay=none ... status=bounced (Host or domain name not found)` — or refused it as an unauthorised relay when the client was not trusted. Reproduced on the lab by restoring the old settings and watching the same message bounce, then fixed and re-sent into the mailbox.

Delivery is by LMTP to Dovecot, whose `auth_username_format = %n` drops the domain before the userdb lookup, so `user@drehtuer.de` and `user@drehtuer.net` resolve to the same system account and land in the same Maildir. Nothing extra is needed in the `imap` role for this — see its row below. Verified on the lab: messages to the account at both domains, and to `postmaster@<alias domain>`, all arrived in one Maildir.

`virtual_alias_domains` is now set explicitly and empty, so the alias map is purely a rewriting table and `virtual_mailbox_domains` is the single answer to "which domains does this host accept mail for". `postfix check` is silent on the result.

**Every alias exists on every domain.** `valiases` generates each `mail.aliases` entry for the primary domain *and* every `domain_aliases` entry, so `postmaster@drehtuer.de` forwards where `postmaster@drehtuer.net` does. The right-hand side always stays on the primary domain, which is where the mailboxes are. `myhostname`/`smtpd_banner` stay on the primary too — one HELO name is correct, and it is the name in the certificate.

**Recipients are validated during the SMTP transaction, and this host no longer emits backscatter.** `virtual_mailbox_maps` was empty until 2026-08-17 while `virtual_mailbox_domains` named both domains, so Postfix answered `250 2.1.5 Ok` to every address in either one, handed it to Dovecot over LMTP, was refused there, and generated a bounce afterwards — to an envelope sender that on spam is forged. `/etc/vmailbox` is now rendered from `users.users` crossed with `[domain] + domain_aliases` plus every `mail.aliases` entry, with an explicit `smtpd_reject_unlisted_recipient = yes`.

What made the size of it visible was the DMARC data. Two aggregate reports on 2026-08-17, from Google and from PayPal, each recorded one of those bounces being discarded by the receiver under this domain's own `p=reject` — PayPal's with `<envelope_from/>` empty and `<scope>helo</scope>`, which is what identifies a null-return-path DSN rather than forged mail from elsewhere. The logs then named the main culprit: one role address carried over from the old `drehtuer.de` host but never written into `mail.aliases`. It took 51 messages between the MX cutover on 2026-08-16 and 2026-08-18 and bounced every one. The senders were forged `support@paypal.com`, `support@google.com`, `support@cnn.com` and similar, so each bounce went to an innocent third party. It is a real address and is now an alias; the map would otherwise have kept rejecting it. The address itself is in the vault-encrypted host vars, not here.

Verified on `carcosa` on 2026-08-18 by SMTP conversation. `RCPT TO:<definitely-no-such-user-9876@drehtuer.net>` is answered `550 5.1.1 ... User unknown in virtual mailbox table`, where the identical conversation on 2026-08-16 got `250 2.1.5 Ok`; the same holds for an unknown address at the alias domain. Two results there are worth keeping. **Postfix consults `virtual_alias_maps` before the mailbox map when deciding whether a recipient exists** — `postmaster@` at both domains is accepted although it is an alias and has no mailbox, which is the assumption the whole design rests on and was not obvious enough to take on trust. And **`permit_mynetworks` does not bypass the check**: the probe ran over loopback and was still refused, because `smtpd_reject_unlisted_recipient` is evaluated independently of the restriction lists. `root@mail.<domain>` still resolves, being in `mydestination` and validated against `local_recipient_maps` instead.

Note which way this cuts before editing either list: the map does not improve delivery, it restricts it. An address missing from it is refused at the door rather than mis-delivered, which is why `roles/mail` asserts `postmaster` is present in the source data before rendering — losing that one would also lose the address the DMARC reports are delivered to.

**Postfix's own bounces are signed, so the ones that remain can authenticate.** `internal_mail_filter_classes` was unset, which meant mail the bounce daemon generates never reached the RSpamd milter and went out unsigned; with a null return path the receiver falls back to the HELO name for SPF, and `mail.<domain>` had no record. Unsigned and unaligned under `p=reject` is discarded, so a genuine delivery failure never reached the sender who caused it. Setting it to `bounce` fixes that — the DSN's `From:` is `MAILER-DAEMON@$myorigin`, i.e. the primary domain, which aligns strictly under `adkim=s` and, unlike SPF, survives forwarding. `notify` is deliberately excluded: those go to postmaster locally.

Verified on 2026-08-18 by provoking a real DSN and reading RSpamd's own log for it: `BOUNCE(-0.10){DSN;}` alongside `DKIM_SIGNED(0.00){drehtuer.net:s=s202608;}`. Before the change that message would not have appeared in that log at all. `mail.<domain>` also has an SPF record in both zones now, and all three secondaries serve it — but that fixes plain HELO-based SPF checking only, because under `aspf=s` a subdomain never aligns. The signature is what makes the DMARC evaluation pass.

Order matters if these are ever separated: signing bounces makes them *deliverable*, so doing it without recipient validation would mean successfully delivering backscatter to forged senders rather than having receivers drop it.

**Handlers compile the maps before restarting or reloading Postfix**, and the order in `handlers/main.yml` is what enforces it — Ansible runs handlers in definition order, not notification order. With the restart/reload pair first, a from-scratch provision starts Postfix against a `main.cf` naming a `virtual_mailbox_maps` whose `.db` does not exist yet, and an unavailable table there means `451 4.3.0` to every recipient. An unavailable *alias* table had only meant no rewriting, which is why the old order survived as long as it did.

**`mail.<domain>` is delivered by the local transport, not the virtual one.** The name appears in both `mydestination` and `virtual_mailbox_domains`, which Postfix advises against precisely because it will not say which wins. Settled by experiment on 2026-08-16: a message to `root@mail.<domain>` was handled by `relay=local`, which applied the `root` alias from `mail.aliases` and only then passed the rewritten `<account>@<domain>` to Dovecot over LMTP. So mail to that name does reach the Maildir, but by way of the alias rather than because the virtual entry matched. Worth knowing before editing either list — see `doc/TODO.adoc`.

| `imap`
| Dovecot core/IMAP/LMTP/Sieve. Spam is filed at delivery time by a `sieve_before` script keyed on `X-Spam: Yes`, so it lands in the user's `Spam` mailbox rather than the inbox. Training is a *separate* `TrainSpam` folder: moving a message into it teaches RSpamd spam, moving one out teaches ham - keeping it apart from `Spam` means the automatic filing of spam is not itself taken as a training signal. Both need `imap_sieve` loaded in a `protocol imap` block, without which the `imapsieve_mailbox*` rules are silently inert, and all sieve scripts are compiled by a task rather than a handler, so a `.svbin` always exists for Dovecot to use.

**Maildir import.** `maildir-import <[user@]host>[:<path>]` is deployed to `/usr/local/bin` for migrating an account off another server, and is the companion to `rspamd-train-bulk` below: that one seeds the classifier from a corpus already on disk, this one is what fetches the corpus — and the rest of the mail — in the first place. It copies the message files with `rsync` rather than fetching over IMAP, which preserves flags and folder structure for free (both live in the Maildir filename and directory name) and, more importantly, cannot trip the `imapsieve` rules above: those fire on IMAP `COPY` into and out of `TrainSpam`, so an IMAP-based migration would mass-train RSpamd as a side effect of the copy. Spam folders are diverted to a staging directory instead of imported, since on a real mailbox they are usually most of the messages and none of the value. Nothing runs with `--delete`, so it is additive on the destination and read-only on the source, and re-running it copies only what is new.

Two things about it are worth knowing before using it. It reads `imap.conf.maildir`, the same variable `dovecot.conf` renders `mail_location` from, so an import cannot write mail somewhere Dovecot is not looking. And it must be run as the user whose mail is being imported — which means SSH to the source uses *that user's* credentials, and **agent forwarding is not available on a host this repo configures**: `roles/sshd` sets `AllowAgentForwarding no`, so `ssh -A` leaves `SSH_AUTH_SOCK` unset here and every connection to the source fails with `Permission denied (publickey)`. Do not relax that setting for a migration; give the host a key of its own, authorize it on the source with `restrict,from="<host>"`, pass it with `-e "ssh -i <key>"`, and remove it afterwards. `--help` spells the sequence out.

Proven on the `drehtuer.de` migration on 2026-08-16: 21312 messages across 117 folders, verified message-by-message against the source with nothing missing, merged into a live mailbox without disturbing the mail that had already arrived here.

**Rotating the Dovecot log is this role's job, because diverting it was this role's decision.** Dovecot's package ships no logrotate config, and correctly so: by default it logs to syslog, which rsyslog already rotates. `log_path` in `dovecot.conf` is what moves it to a file of its own — so the file exists only because this role asked for it, and until 2026-08-16 nothing rotated it. On `carcosa` that had gone unnoticed for a year: 63 MB and 305410 lines in one file, the oldest entry a year old, while every other service there (nginx, rspamd, mariadb, redis, php-fpm, fail2ban) had rotation from its own package. The path is `imap.conf.logfile`, read by both `dovecot.conf` and the logrotate template so the two cannot drift; note that `roles/fail2ban`'s `dovecot` jail names the same file independently in its own `logpath`.

`copytruncate` is deliberately not used — it copies and then truncates, losing anything written in between, which is the wrong trade on what is also the audit trail for failed logins. `doveadm log reopen` in a `postrotate` script renames and reopens instead, guarded so that logrotate does not report the whole run as failed when Dovecot is down.

Worth knowing if this is ever tested by hand: `logrotate -d /etc/logrotate.d/dovecot` **fails** with *"parent directory has insecure permissions"*, because `/var/log` is group-writable by `syslog` and a bare fragment does not inherit the `su root adm` that `/etc/logrotate.conf` sets globally. That is an artefact of testing the fragment in isolation, not a fault in the config — run `logrotate -d /etc/logrotate.conf` instead, which is how it actually runs. Verified by forcing a rotation: the old file was preserved, a fresh `0600 root:root` file created, and Dovecot confirmed writing to the new inode while the rotated one stayed frozen.

**`sievec` is invoked with `-c /etc/dovecot/dovecot.conf`, and the flag is load-bearing.** Without it `sievec` does not read Dovecot's configuration at all — it compiles against a standalone default set of extensions — so `sieve_plugins` and `sieve_extensions` never apply and both training scripts fail to compile with ``unknown Sieve capability `vnd.dovecot.pipe' `` / ``unknown Sieve capability `imapsieve' ``. That reads like a missing package and is not one: the plugin `.so` files are installed and `doveconf plugin/sieve_plugins` reports them correctly; only the compiler was looking elsewhere. It failed the whole role, and was found on a from-scratch VM provision rather than on `carcosa`, whose `.svbin` files predate the check. Deploys Sieve-pipe scripts that call RSpamd's ham/spam learning API so users can train the spam filter via IMAP move-to-folder actions.

**`auth_username_format = %n` is what makes the multi-domain setup work, and it is load-bearing rather than cosmetic.** `%n` is the local part alone, so the domain is dropped before *every* auth request — not only logins, but also the recipient lookup Dovecot performs when Postfix hands a message over on LMTP. One account therefore has one inbox no matter which of this host's domains the mail was addressed to, and a client authenticates identically whether it is configured with `user@drehtuer.net`, `user@drehtuer.de` or a bare `user`. Accounts are system users (`passdb pam` / `userdb passwd`), which have no domain to begin with, so there is nothing here that *could* distinguish them per domain. Which domains reach this point is entirely the `mail` role's decision, via `virtual_mailbox_domains`. The role reads `domain_aliases` only to name the covered domains in a comment in `dovecot.conf`; no Dovecot setting is derived from it.

Worth knowing rather than discovering: because the domain is *discarded* rather than checked, an IMAP client offering `user@anything.example` authenticates exactly as one offering a served domain. Confirmed on the lab, alongside the intended cases — `<account>`, `<account>@lab.lan` and `<account>@lab.test` all logged in to the same 7-message INBOX, and `doveadm user` resolved all three to uid 1000 and that account's home. Nothing is reachable that would not otherwise be, since it is one account either way, but Dovecot is not the component that decides which domains this host answers for.

| `spam`
| RSpamd: installs the package, wires it to the shared Redis instance, configures `actions.conf` and the controller web UI (password-protected via a vault-encrypted `htpasswd`, reverse-proxied through nginx at `spam.<domain>`, for every domain in `http.domains`). Inbound filtering works end to end (see the pipeline description below), and outbound mail is DKIM-signed.

**Outbound DKIM is RSA-2048 on both domains, published and verified.** Selector `s202608`; `s202608._domainkey.drehtuer.net` and `s202608._domainkey.drehtuer.de` are served by all three Hetzner nameservers. Each record's `p=` was checked byte-for-byte against the public half derived from the private key RSpamd signs with, rather than transcribed from the generator's `.txt` and hoped for, and the rendered zone was reassembled from its quoted strings and compared back before deploying. A real signed message then round-tripped through verification against live DNS: `R_DKIM_ALLOW` with `DKIM_TRACE [<domain>:+]` for both.

**`drehtuer.net` was ed25519 until 2026-08-16, and that was a real deliverability problem rather than a cosmetic one.** The key predated the role settling on RSA and the generator would never have replaced it, since it refuses to regenerate an existing key. Record and key agreed — but Gmail, Microsoft 365 and Yahoo do not verify `ed25519-sha256` at all; Gmail answers `dkim=neutral (no key)`, i.e. it behaves as though no key were published. Independent testing in April 2026 put support at 9 of 19 providers. Under this domain's `p=reject; adkim=s; aspf=s`, that left DMARC resting entirely on SPF at the three largest receivers — and SPF is exactly what forwarding breaks, which is the case DKIM exists to survive.

**The rotation used a new selector rather than a new key under the old one**, which is what made it seamless. Replacing the key under `mail` would have left up to a TTL's worth of receivers holding the cached old record while new signatures arrived against it; a selector never seen before cannot be cached wrong. The order matters and is the whole trick: generate the keys, publish the records *alongside* the old ones, verify they resolve, and only then point signing at them. Doing it in one step signs mail against a record that is not published yet.

The superseded `mail._domainkey` records for both domains are deliberately **still published**, so that any message signed before the switch still verifies. Removing them is tracked in `doc/TODO.adoc`.

Because the selector is one global setting shared by every served domain, rotating it rotated `drehtuer.de` too. Its key was already RSA, so nothing was wrong with it — but a single selector is what stops the signing config drifting out of step with the keys on disk, and that property is worth more than avoiding one redundant key.

Records are split across eight or nine quoted strings. DNS concatenates them with nothing in between, so the split is invisible to a verifier; each fragment must stay under both the 255-character limit for one TXT character-string and this repo's 80-column YAML rule. The folded scalar joins those lines with a space that lands *between* quoted strings — folding one into the middle of the base64 would break the key.

One RSA key per served domain, generated into `/var/lib/rspamd/dkim/<domain>.<selector>.key` by a script the role deploys, with the matching DNS record written beside it as `.txt`. Generation is idempotent - an existing key is never regenerated, since that would invalidate a record already published - and the task reports `changed` only when a key was actually created. Signing is configured with a single `path = ".../$domain.$selector.key"` rather than per-domain blocks, so every served domain is covered by one line that cannot drift out of step with the keys. RSA rather than Ed25519, for the reasons above. `allow_missing_key = false`, so the host will not sign as a domain it holds no key for. Note the interaction between "never regenerated" and a rotation: because the generator skips any key that already exists, changing the selector is what creates new keys — and it is also why keys generated by hand ahead of a rotation are left untouched when the role next runs.

**Inbound pipeline.** RSpamd runs as a Postfix milter and every message is scanned. `actions.conf` deliberately sets `reject = null`: spam is *delivered and flagged*, not refused, so a false positive stays recoverable by the user. `milter_headers.conf` adds the verdict to the message - `X-Spam: Yes` above the `add_header` threshold, plus `X-Spam-Status` and `X-Spamd-Result` listing every symbol that fired. `force_actions.conf` is the one exception to not rejecting: a message whose sender domain publishes `-all` and does not authorise the sending host (`R_SPF_FAIL`), or which carries a DKIM signature that does not verify (`R_DKIM_REJECT`), is refused outright. Mail with no SPF or DKIM policy at all is unaffected and accepted.

**Bulk training.** `rspamd-train-bulk <spam|ham> <path>...` is deployed to `/usr/local/bin` for seeding the classifier from mail exported from elsewhere. It takes a directory (searched recursively, Dovecot index files ignored), an mbox (split into individual messages first), or a single file, and batches them through `rspamc`. Messages below 256 bytes are skipped, because RSpamd refuses anything with too few tokens to be worth learning. Re-running over the same corpus is safe: already-learned messages are reported as skipped, not as failures, and the exit status stays 0. The role never invokes it - it is a tool, run by hand with a corpus.

Note that this role needs `roles/dns`: RSpamd's resolver is pointed at `127.0.0.1`, so without `unbound` every DNS-based check silently returns nothing.

The vhost used to `include locations-enabled/letsencrypt.conf`, which no role creates. A non-glob `include` of a missing file is a fatal nginx error rather than a warning, so this vhost had never actually loaded. Removed: the ACME challenge is served by the port-80 catch-all, so a TLS vhost has no reason to include it at all. It loads now - `spam.conf` is enabled on the host and `https://spam.<domain>/` answers 401, i.e. the basic-auth prompt in front of the controller UI.

**Rejection on SPF failure is real, and has been observed rejecting.** `force_actions.conf` turns `R_SPF_FAIL` into a reject regardless of score, and on 2026-08-16 two real inbound messages were answered `T (reject)` — one of them scoring 3.80 against a required 6.00, which is the useful part of the evidence: below the spam threshold, score-based logic would have taken no action, so something forced it. The DKIM equivalent has never fired on a real message. Note that RSpamd's log keeps four daily generations, so this evidence rotates away quickly; an empty log is not proof that nothing was rejected.

| `talk`
| Nextcloud Talk's high-performance backend: `nextcloud/aio-talk`, which bundles the signaling server, Janus as the WebRTC media gateway, NATS between them and eturnal as the TURN server. Pinned by tag *and* digest, the stance `cloud` takes with Nextcloud's checksum. The role also registers all three with Nextcloud through `occ talk:signaling:add`, `talk:turn:add` and `talk:stun:add` — without that the backend runs and Talk never uses it.

**What it buys.** Without a backend, Talk connects browsers peer to peer and stops scaling at roughly four participants, because every client sends its stream to every other client. With it, each client sends once to Janus, which forwards — which is why this needs real media ports rather than only an API.

**Host networking, for the opposite reason to `fail2ban_ui`.** There it kept the listener on loopback; here TURN must be reachable from the internet, and a published port would be DNATed — which for TURN means the addresses it advertises to clients are not the ones packets arrive on, and media silently fails to establish. Host networking gives it the host's own addresses. The signaling server binds `talk.signaling_port` as a consequence and is deliberately not opened in the firewall: nginx terminates TLS and proxies the WebSocket in from loopback.

**Only 3478 is open, TCP and UDP.** That is the registered TURN port and the one clients try first; it is also the media path, which is why UDP matters.

**Three shared secrets, none interchangeable** — `turn` between clients and the TURN server, `signaling` between Nextcloud and the signaling server, `internal` between the signaling server's own components. The role refuses to run with any of them empty.

**Rotating one means deleting the Nextcloud entry first.** `talk:signaling:add` and `talk:turn:add` append; there is no update. The role compares the stored secret against the wanted one and deletes before re-adding, which is also what keeps it idempotent. That comparison **parses** the JSON rather than grepping it: the secrets are base64 and JSON escapes `/` as `\/`, so a substring test silently fails for any secret containing a slash — which showed up as the delete/re-add pair running on every deploy.

**The `occ talk:*:list` commands print the stored secrets.** Every task reading them carries `no_log`. Reading one unredacted is how two of these secrets ended up in a terminal on 2026-08-16 and had to be rotated; the same shape of mistake as the TSIG one recorded under `nsd`.

| `upgrade`
| Ubuntu release upgrade (e.g. 24.04 → 26.04). Generic, not tied to any specific release: the target is read from `upgrade.target_release` (unset by default, so the role is a no-op until a host explicitly sets it), and the actual version to move to is resolved by Ubuntu's own `do-release-upgrade` tooling rather than being passed literally. Fully updates and dist-upgrades the current release first, then runs `do-release-upgrade` non-interactively (via `async`/`poll`, since the command can run for over an hour and briefly disrupts networking), reboots, and re-verifies the release afterwards. Deliberately **not** wired into any other playbook: `playbooks/upgrade.yml` tags its tasks `never`/`release-upgrade`, so it only runs when explicitly requested with `--tags release-upgrade` (`invoke run-playbook --playbook=playbooks/upgrade.yml --tags=release-upgrade`, after setting `upgrade.target_release` in the target host's `host_vars`).

| `fail2ban_ui`
| The `swissmakers/fail2ban-ui` web interface for fail2ban, run as a Compose stack and reverse-proxied at `f2b.<domain>` for every served domain. The first consumer of the `docker` role. Upstream ships no official UI, and the older `fail2web`/`fail2rest` pair has been unmaintained for years.

**The image is pinned by tag *and* digest**, the same stance `cloud` takes with Nextcloud's checksum — a tag can be moved under you, a digest cannot. The multi-arch *index* digest rather than one platform's, so the pin survives on a host of another architecture. Bumping the version means editing both, which is the point.

**Host networking with a loopback bind, not a published port.** `BIND_ADDRESS=127.0.0.1` under `network_mode: host` puts the listener on the host's loopback and provably nowhere else — `ss -ltn` is the whole story. A published port would instead be DNATed and traverse `FORWARD` rather than `INPUT`, which is exactly what `firewall.docker.published` exists to cover; this way there is no port to forget to list. Note the trap if the two are ever swapped: on a *bridge* network that same `BIND_ADDRESS` would bind the container's own loopback and be unreachable from nginx.

**The basic-auth credential in front of it is the entire access control.** The UI has no password authentication of its own — upstream supports OIDC only (Keycloak/Authentik/Pocket-ID) and this host runs no identity provider. That is a stronger dependency than the RSpamd controller behind `spam.<domain>`, which has a password underneath as well. The container mounts fail2ban's control socket and `/etc/fail2ban` read-write, so whatever reaches it can ban an arbitrary address — including yours — and unban an attacker.

**It writes to the same `jail.local` that `roles/fail2ban` owns.** Its Global Settings are written into that file's `[DEFAULT]` section, so anything changed through the UI is reverted by the next `playbooks/fail2ban.yml` run and shows as drift in between — the same shape as the Nextcloud `trusted_domains` caveat. Verified that it does *not* touch the file merely by starting: after deploying, `jail.local`'s mtime was unchanged and `check-drift` on the fail2ban role reported nothing. `JAIL_AUTOMIGRATION` is deliberately never set; it rewrites `jail.local` into `jail.d/*.local`, which upstream itself marks experimental and advises against in production.

`UPDATE_CHECK` and `DISABLE_EXTERNAL_IP_LOOKUP` are set so the container makes no outbound calls of its own. Verified on the lab that it survives the Docker restart the `firewall` role triggers on every rules change — `live-restore` keeps it up rather than bouncing it.

| `monitoring`
| Prometheus, Alertmanager and node_exporter, all bound to loopback, with firing alerts delivered as mail through the Postfix this repo already configures (phase 1); plus Grafana behind an nginx vhost at `status.<domain>` (phase 2). `roles/firewall` opens no port for any of it — nginx is the only way in, and only to Grafana.

**Deployed on `carcosa` since 2026-08-16, after the lab.** It converges and is idempotent under molecule, on a real 24.04 guest and on production alike, and in each case the end state was checked rather than inferred from a green run: all three listeners on `127.0.0.1` and nowhere else, nothing at all on 9094, no failed units, all three scrape targets `up` and both rule groups loaded. The only alert firing on `carcosa` is the `Watchdog`, which is what a healthy host should look like — the baseline taken before the deploy had no failed units, 4% of 3.6 TB used, 1% of inodes and 95% of memory available, so nothing else had any reason to.

**Installing it produces a handful of stray samples, once, and they are harmless.** `apt` starts the service before Ansible can write a configuration for it, so Prometheus runs briefly under the *packaged* `prometheus.yml` and scrapes its `localhost:9090`/`localhost:9100` targets a few times before the role replaces the file. The result is a second set of series under an `instance` label this host will never use again — four samples in total here — which drop out of instant queries once past Prometheus's five-minute lookback and were confirmed gone. Worth knowing only because `up` briefly returns five series where the API reports three targets, which looks like duplicate scraping and is not; the range query is what distinguishes them, since an instant query reports the *evaluation* timestamp rather than the sample's and therefore makes every series look freshly collected.

**The alert mail arrives, which is the half molecule cannot show.** On `yuggoth`, which has a real Postfix and Dovecot, the whole chain ran end to end — `vector(1)` evaluated, `Watchdog` fired, Alertmanager matched it to its own route, connected to Postfix on `127.0.0.1:25`, and the message was delivered over LMTP into the Maildir as `[FIRING:1] Watchdog (yuggoth watchdog)`. Both labels in that subject are worth reading: `yuggoth` is `external_labels.host` and `watchdog` the severity, so the rendering of both is confirmed by the artefact rather than by inspection. Alertmanager reports one notification sent and zero failed. In a container the same run correctly ends at a refused SMTP connection, which is why this had to be tested somewhere with a mail server.

**Every alert selector was checked against real data, which matters more than the syntax check.** promtool proves an expression parses; it cannot prove the metric exists. A rule naming a metric or label that never appears is silently unable to fire, and reports nothing wrong for as long as it is deployed — the same failure the `postfix` fail2ban jail had, where a filter watching the wrong systemd unit reported `Total failed: 0` on a host with hundreds. Each selector was therefore queried on the live host and all ten returned series: filesystem space, the `predict_linear` trend, inodes, read-only state, memory, load per CPU, clock sync and offset, 221 systemd unit states and `up`. Zero empty. The traffic rules were checked separately because the interface is fact-derived and a wrong name is exactly this kind of silent miss: the rendered rule carries `device="enp0s2"`, `ip route get` agrees, and the rate query returns a series.

The `promtool` split was confirmed on the real release as well — the run reports `skipped=1`, that skip being the separate-package task correctly not needed on 24.04.

**apt rather than containers, which is the opposite of the `fail2ban_ui` and `talk` decision and for a concrete reason.** All three are in the Ubuntu archive on 24.04 and 26.04 alike, and node_exporter in particular is a poor container citizen: it would need the host's PID and network namespaces plus bind mounts of `/proc`, `/sys` and `/`, which is every bit of isolation a container exists to provide. Grafana is the one piece of this stack *not* in the archive, which is why phase 2 will be the containerised half.

**Both servers listen on every interface out of the box, which is why `/etc/default/*` is templated at all.** Debian patches the config and storage paths sensibly — `/etc/prometheus`, `/var/lib/prometheus/metrics2` — but not the bind address, so `0.0.0.0:9090` and `:9093` are what the packages give you. The role owns those bindings the same way `roles/database` owns MariaDB's, rather than inheriting them from a package that could change them under it.

Alertmanager needs a second override that is easy to miss: it opens a *further* listener for HA gossip on `0.0.0.0:9094` unless `--cluster.listen-address` is set to the empty string. That is a port on both public addresses, for a cluster of one. Emptying it disables HA mode outright, confirmed by the API reporting `cluster: disabled` and by nothing listening on 9094.

**`promtool` is packaged differently on either side of the release upgrade this host is waiting for.** On 24.04 it ships *inside* the `prometheus` package and no `promtool` package exists; on 26.04 `prometheus` carries only the server and promtool is split out. The role needs it on both, since it is what validates the generated configuration, so it tests for the binary rather than comparing release numbers — which also carries the host across the upgrade unattended, the split package's arrival removing the bundled binary and the next run installing the replacement. Found by the molecule scenario failing on a 24.04 image, after the package index had been misread as saying otherwise.

**Every generated file is validated before it is installed**, the same stance as `nginx -t`, `sshd -t` and `nsd-checkzone` elsewhere here: `promtool check rules` on each rule file, `promtool check config` on `prometheus.yml`, `amtool check-config` on `alertmanager.yml`, all as `validate:` so a bad file is never written. The rules are deployed *before* `prometheus.yml` and that order is load-bearing — `promtool check config` resolves the `rule_files` glob, so validating the configuration first would check it against rules not yet on disk.

**The alert rules are mostly this host's own history.** Beyond the obvious disk, memory, load and clock checks: inode exhaustion, because a Maildir is one file per message and Nextcloud's data directory is millions of small ones, so this host can run out of inodes with space to spare and see it reported as "disk full"; a disk *trend* via `predict_linear` as well as a threshold, because on a filesystem that grows with every upload the useful question is "when" rather than "how much"; and `node_systemd_unit_state{state="failed"}`, which turns `systemctl list-units --state=failed` into a continuously checked invariant rather than something someone remembers to run — the failure the masked `unbound-resolvconf` unit hid in plain sight for months.

The traffic thresholds are the ones to distrust. `HostEgressHigh` and `HostIngressHigh` are scoped to the default route's interface, by the same fact and the same no-fallback reasoning as `firewall.docker.wan_interface`, but the numbers are placeholders: the right value cannot be known before this host has a baseline. Treat the first weeks as warn-only and tune. Egress is the interesting direction — an abused relay, a compromised account and a bulk copy of the data directory all look alike from here.

**The Watchdog alert is the only self-check available on one host.** It fires permanently and is routed to a mail of its own on a fixed interval, so that its *absence* carries information: a day with no Watchdog mail means scraping, rule evaluation, routing or SMTP has stopped, rather than that nothing was wrong. This is the same reasoning as the `nsd` re-signing timer — scheduling a job proves it started and nothing more — and it is needed here because the monitoring system delivers its own alerts through a service it is also monitoring. If Postfix is down, the alert about Postfix cannot be mailed.

What that still does not cover: a host that is powered off or off the network sends nothing, and the silence is indistinguishable from a working system with nothing to report. Closing that needs something off-host, and is recorded in `doc/TODO.adoc` rather than solved here.

**No inhibit rules, deliberately.** The obvious one — critical suppresses warning — cannot be written correctly: the two disk severities are separate alert names, so matching on `alertname` inhibits nothing, and dropping it from the match would let a single critical silence every unrelated warning on the only host there is. A duplicate mail is a smaller problem than a silenced one.

**Grafana is the one piece of this stack that is a container, and only because it is not in the Ubuntu archive.** Everything else is a package. It runs with `network_mode: host` and binds `127.0.0.1:3000` — the `fail2ban_ui` pattern, and for the same reason: with host networking that address is the host's own loopback, so `ss -ltn` is the whole story and there is no published port to remember to list in `firewall.docker.published`. On a *bridge* network the identical setting would bind the container's loopback and be unreachable from nginx, which is the tempting and wrong fix if the two are ever swapped. Pinned by tag and multi-arch index digest, verified against the registry rather than copied from a tag listing.

**This role took `status.<domain>` over from a static placeholder, and the handover needs a deletion the `http` role will not do.** That name was an entry in `http.sites`; it is gone from the inventory now, but the `http` role renders and enables that list without ever removing a vhost dropped from it, so the old `status.conf` would simply stay on disk and claim the same `server_name`. nginx resolves a duplicate by keeping whichever loaded first and warning — and `nginx -t` calls that a success. The role therefore deletes both the file and its symlink itself. The general gap is in `doc/TODO.adoc`.

**The basic-auth credential has to be stripped before the request reaches Grafana, and nothing but a browser shows it.** nginx does not consume the credential it has just checked: it forwards the `Authorization` header upstream, and Grafana reads a `Basic` header as a login attempt against its own user database. The outer credential is not a Grafana user, so Grafana answers 401 with its own `WWW-Authenticate`, the browser re-prompts with the same credential, and the page never loads. `curl` never sees the loop because it stops at the first 401. `proxy_set_header Authorization "";` is the fix, and the evidence it works is that an unauthenticated request now gets Grafana's own 302 to `/login` rather than a 401.

**Grafana will not run under the shared CSP.** `conf-server/security.conf` allows inline script and style but not `'unsafe-eval'`, which Grafana's expression and transformation engine needs, nor `blob:` workers, which its rendering does. Under that policy the page returns 200, loads its JavaScript and renders nothing. The vhost therefore repeats the whole header set inside `location /` with those two additions — repeats rather than extends, because nginx drops every inherited `add_header` the moment a block declares one of its own, the same rule `roles/cloud` works around. Confirmed on the lab that exactly *one* CSP header is sent, carrying both additions: two would be intersected by the browser and put us back where we started. The file is still included for the dot-file deny it also carries.

**The admin password is not in the compose file.** It is in an `admin.env` written 0600 by a task carrying `no_log`, referenced by `env_file:`, so that a `--diff` from `invoke check-drift` cannot print it — the same separation the `nsd` role makes for its TSIG secret. The nginx basic-auth credential is a second, independent secret, vault-encrypted as a `.aes256` htpasswd like `spam` and `fail2ban_ui`.

**The datasource and dashboard are provisioned from files, and the datasource uid is fixed rather than generated.** The dashboards reference it, and a generated uid would differ per host and leave every panel pointed at a datasource that does not exist — which Grafana renders as an empty panel rather than as an error. The dashboard JSON is validated with `python3 -m json.tool` before it is installed, because Grafana logs a malformed dashboard and carries on without it, so the failure is a missing page rather than a failed run.

**Grafana and Prometheus share the vhost; Alertmanager deliberately does not.** Grafana at `/`, Prometheus at `/prometheus/`, both behind the one basic-auth credential. Prometheus earns its place by showing what Grafana cannot render at all - scrape-target health, rule state and the current alert list. Alertmanager was exposed at `/alerts/` for a few hours on 2026-08-16 and then removed: its interface adds little over the alert list Prometheus already shows, and the one thing it does add - creating silences - is exactly what should not sit behind a single shared credential, since a silence switches monitoring off and nothing else records that it happened. It stays on loopback, and silences are made with `amtool` on the host.

**The Prometheus that Ubuntu ships has no React UI, and that is why the paths look odd.** The package contains `web/no-ui/index.html` and an `install-ui.sh` rather than the bundled interface, so `/prometheus/` redirects to `/prometheus/classic/graph` and the modern paths - `/alerts`, `/rules`, `/targets` - answer 404 while their `classic/` equivalents serve normally. Nothing is broken; the classic interface is complete, and `/prometheus/classic/alerts` is where the firing alerts are.

**The path prefix is served by Prometheus, not stripped by nginx, and that is the part that has to be got right.** It is started with `--web.external-url` ending in its path, which becomes its route prefix, so it serves and self-links under it. Stripping the prefix at nginx instead would leave it redirecting `/` to `/classic/graph` at the vhost root - landing on Grafana. A route prefix also moves *every* path it serves, `/metrics` included, so the self-scrape names `/prometheus/metrics`; miss that and the target simply goes down.

Alertmanager has no route prefix precisely because it is not served through the vhost. Note what that coupling means if it is ever exposed again: Prometheus posts alerts to Alertmanager's API, so a route prefix there has to be matched by `path_prefix` under `alertmanagers` in `prometheus.yml`, or Prometheus posts to a 404 and alerting stops without a word. Both directions of that change were made and verified within a day, so the failure mode is known rather than theoretical.

Worth knowing when checking the alert path by hand: Alertmanager keeps its notification log on disk, so restarting it does *not* re-notify for an alert it has already sent, and `alertmanager_notifications_total` resetting to zero after a deploy means the counter restarted rather than that delivery broke. Inject a fresh alert with `amtool` instead of waiting for the Watchdog.

**Deployed on `carcosa` since 2026-08-16.** Idempotent; the container bound to loopback and nowhere else; the old `status.conf` gone; nginx answering 401 without credentials and serving Grafana's login page with them, on the alias domain as well as the primary; exactly one CSP header carrying both additions; the datasource and dashboard both present; and — the check worth more than the rest — a query pushed *through* Grafana's datasource proxy returning live series, which proves Grafana can reach a Prometheus that has no vhost of its own. Every other vhost still answers as before, checked rather than assumed after the reload. What none of that shows is whether the interface renders, since that needs a browser and the CSP is exactly the sort of thing that fails only there.

**Two things only the production run surfaced, both now fixed.** Neither broke anything; both left a permanent error in the log of the one service whose job is to report problems, which is the same reason the masked `unbound-resolvconf` unit was worth chasing.

The read-only provisioning mount *replaces* Grafana's whole `provisioning` tree, and the image ships six directories there - `access-control`, `alerting`, `dashboards`, `datasources`, `notifiers`, `plugins`. Mounting only the two this repo writes into made Grafana log a read failure for the others on every start. All six are created now, four of them deliberately empty.

Grafana also has a fourth outbound path that the three `analytics` settings do not cover: `preinstall_disabled` defaults to false and `preinstall_auto_update` to true, so on every start it asks grafana.com about its preinstalled plugins and tries to update them. Here it also *failed*, because the bundled plugin directory lives inside the image and is not writable by the uid this runs as - `Failed to install plugin pluginId=elasticsearch ... permission denied` on every start. `GF_PLUGINS_PREINSTALL_DISABLED` removes the error and the network call together.

Worth knowing for the next deploy: Grafana runs its database migrations before it binds, which on a first start takes a couple of minutes, and `status.<domain>` answers 502 for that whole window. The nginx log records it as `connect() failed (111: Connection refused) ... upstream: http://127.0.0.1:3000/`, which is expected rather than a fault.

== Role ordering constraints

Nothing asserts these; they are why an umbrella playbook is wanted (`doc/TODO.adoc`). Each has bitten a from-scratch provision or would.

* `roles/spam` depends on `roles/dns`.* `options.inc` points RSpamd's resolver at `127.0.0.1`, so without `unbound` every DNS-based check - SPF, DKIM, DMARC, RBLs - silently returns nothing. No error is logged; spam filtering just quietly does much less. Deploy `playbooks/dns.yml` before `playbooks/spam.yml` on a fresh host, and fold the ordering into the umbrella playbook when it exists.
* `roles/cloud` depends on `roles/database`.* `memcache.locking` in `config/cache.config.php` points at the shared Redis instance, so an unreachable Redis makes Nextcloud return errors rather than degrade. Both run on the same host and `playbooks/database.yml` provisions Redis, so this is only an ordering constraint on a fresh host - one more for the umbrella playbook.
* `roles/fail2ban_ui` depends on `roles/docker`, `roles/fail2ban` and `roles/http`.* The engine and Compose v2, the socket it is a front end for, and nginx plus a certificate covering `fail2ban_ui.subdomain`. Nothing asserts this; it is one more ordering constraint for the umbrella playbook. Note also that `fail2ban_ui.subdomain` must appear in `http.letsencrypt.subdomains` or the vhost is served with a certificate that does not cover it — nothing enforces that pairing, exactly as with the `spam` role.
* `roles/monitoring` depends on `roles/docker`, `roles/http` and `roles/mail`.* The first two only for its Grafana half — the engine and Compose v2, and nginx plus a certificate covering `monitoring.grafana.subdomain`, which must appear in `http.letsencrypt.subdomains` exactly as with `spam`, `talk` and `fail2ban_ui`. The `mail` dependency is softer but more surprising: Alertmanager delivers through Postfix on `127.0.0.1:25`, so on a host where `mail.yml` has not run the alerts are generated, queued and retried but never sent, and the only symptom is the Watchdog mail that does not arrive. The collection half needs none of this and is why it deploys first.
* `roles/fail2ban` depends on `roles/http` having run at least once.* The `nginx-http-auth` and `nginx-404` jails point at `/var/log/nginx/*.log`, and fail2ban refuses to start at all when a jail's log file is missing - `ERROR Failed during configuration: Have not found any log file for nginx-http-auth jail`, then `status=255/EXCEPTION`. On a from-scratch provision `fail2ban.yml` runs before `http.yml`, so the service is left dead and `systemctl list-units --state=failed` does not read clean. Restarting it once nginx exists brings all six jails up, so this is ordering rather than configuration - one more constraint for the umbrella playbook, alongside `dns` before `spam` and `database` before `cloud`. Found on a from-scratch VM provision on 2026-08-16; it has never bitten `carcosa`, where nginx long predates the role.

== Known inconsistencies worth double-checking

* *OCSP stapling is configured and can never work.* `ssl_stapling on` and a `resolver` pointing at the local unbound are both in `roles/http/files/nginx.conf`, and `openssl s_client -connect drehtuer.net:443 -status` answers "no response sent". The cause is not a misconfiguration to chase: Let's Encrypt has retired OCSP, and the certificate on the host carries an Authority Information Access extension with a CA Issuers URI and *no responder URI at all*. There is nothing for nginx to fetch, so the directives are inert rather than broken. They can go; the `resolver` may be worth keeping for anything else that needs run-time name lookup. Tracked in `doc/TODO.adoc`.
* *`$myhostname` is in both `mydestination` and `virtual_mailbox_domains`.* Postfix warns against a domain being in both, and `mail.drehtuer.net` is in both — `mydestination` lists `$myhostname` and `virtual_mailbox_domains` appends it. Pre-existing, unchanged by the multi-domain work above, and evidently survivable, but which address class wins is exactly what the warning exists to say should not be relied on. Establish it on the host before changing either line. Tracked in `doc/TODO.adoc`.
* The `http` and `cloud` roles both run `nginx -t`, but nothing renders and parses the config off-host, so a template change is only proven correct when the role runs. Watch the first run after touching a vhost template.
