= Project Status
include::.attributes-page.adoc[]

This page summarizes what is currently implemented in the repository, as of the state of the `main` branch. It is a snapshot, not a guarantee — verify against the actual roles/playbooks before relying on details here for anything security-relevant.

== Scope

The repo configures a single physical/virtual server, host `carcosa`, serving the primary domain `drehtuer.net` with `drehtuer.de` as a CNAME/alias domain (see `inventories/machines.yml`). All playbooks target `hosts: all`, and the inventory currently defines only this one host.

== Automation model

* Ansible roles under `roles/`, one per service/concern, each wired to a single matching playbook under `playbooks/`.
* No umbrella playbook exists yet — `playbooks/*.yml` are run individually. This is deliberate for now: it keeps each role easy to test in isolation while the configuration is still being built out, and a full from-scratch reinstall isn't needed yet since the target host already exists. An umbrella playbook remains useful future work once the individual roles have settled (see `doc/TODO.adoc`).
* `tasks.py` (python-invoke) wraps `ansible`/`ansible-playbook` with the correct inventory, vault, and become flags. Documented tasks: `ping`, `run-playbook`, `login`, `clean`, plus the lint tasks below.
* Linting is enforced, not advisory: `yamllint --strict` (`.yamllint`), `ansible-lint` at its strictest `production` profile (`.ansible-lint`) and `ruff` check + format (`pyproject.toml`). The whole repo passes all three. They run via `invoke lint` (`--fix` applies what the tools can fix themselves), via the `.githooks/pre-commit` hook on staged files (enable once per clone with `invoke install-hooks`), and in GitHub Actions on pushes to `main` and pull requests (`.github/workflows/lint.yml`). ansible-lint reads `.yamllint` as well, so both YAML tools agree on style. CI has no vault password — it points `ANSIBLE_VAULT_PASSWORD_FILE` at a placeholder file, which is enough because linting never decrypts vaulted values.
* Secrets are stored either as inline `!vault |` values in `inventories/**/*.yml`, or as whole encrypted files (`*.aes256`) decrypted at deploy time via `decrypt: true`. The vault password lives in `vault/secret.txt`, referenced by `ansible.cfg` (`vault_password_file`), and is gitignored.
* Host SSH keys are pre-generated with `roles/sshd/scripts/generate_keys.sh`, vault-encrypted into `roles/sshd/files/`, and the resulting SHA-256 hashes are recorded in `inventories/host_vars/<host>/sshd.yml` so the role can detect drift and only replace the key when its checksum changed.

== Services implemented

[cols="h,d", options="autowidth"]
|===
| Role | Implementation notes

| `system`
| Sets hostname (FQDN), generates/sets locale.

| `apt`
| Updates apt cache, installs a shared base package set (editors, shells, monitoring CLIs, unattended-upgrades, etc.).

| `users`
| Creates groups/users/passwords (all vault-encrypted) and passwordless-sudo for the `sudo` group; installs SSH `authorized_keys`.

| `sshd`
| Installs `openssh-server`; deploys vault-encrypted, per-host ed25519/RSA host keys (intended to be checksum-gated, but the gate is currently a no-op — see `doc/TODO.adoc`) and a shared screened `moduli` file; templates `sshd_config`.

| `firewall`
| `iptables`/`ip6tables` via `iptables-persistent`, default-deny INPUT/FORWARD, SSH connection-rate limiting, and a data-driven allow-list (`firewall.rules.tcp`/`.udp` in `inventories/group_vars/all/firewall.yml`) currently opening TCP 22/25/80/443/587/993 and UDP 53.

| `fail2ban`
| Installs fail2ban with a static `jail.local` covering `sshd`, `postfix`, `dovecot`, `nginx-http-auth`, `nginx-404`.

| `time`
| `ntpsec` with Hetzner NTP servers, hardware clock in UTC, timezone `Europe/Berlin`.

| `cron`
| Installs and enables the `cron` service (other roles add their own cron jobs, e.g. Nextcloud background jobs).

| `dns`
| Installs `unbound` + `unbound-anchor` as a **local, loopback-only DNS-cache/validating resolver** (`interface 127.0.0.1`/`::1`, all other sources refused) and configures `systemd-resolved`. Not yet configured to serve the `drehtuer.net`/`drehtuer.de` zone authoritatively (no zone data, no public listener) — this is planned but not started. The firewall's UDP/53 rule is already in place ahead of this work so it's ready to go once `unbound` is configured to listen publicly. See `doc/TODO.adoc`.

| `database`
| MariaDB (root user/password vault-encrypted, idempotent via a `/root/.mysql_root_password_set` marker file) and Redis (loopback-only, 16 logical DBs), both bound to `127.0.0.1`/`::1` only.

| `docker`
| Installs Docker Engine + Buildx + Compose v2, enables `docker`/`containerd`, adds configured users to the `docker` group. No containers/compose stacks are defined yet — this is deliberate groundwork, laid so a dockerized service can be added later without a separate bootstrap step.

| `http`
| nginx + certbot (`letsencrypt` apt package) + php-fpm. Builds a `conf-server`/`sites-available`/`sites-enabled`/`locations-available`/`locations-enabled` layout, generates a 4096-bit DH param, hardened SSL/security headers (HSTS, CSP, X-Frame-Options, etc.), and obtains a single Let's Encrypt certificate covering the primary domain, the host FQDN, and the `cloud`/`mail`/`spam`/`status`/`www` subdomain aliases (`http.letsencrypt.aliases`). Serves a `status.<domain>` vhost, an HTTP→HTTPS redirect vhost, and a `mail.<domain>` vhost (per-role site configs are added by the `cloud`/`spam` roles).

| `cloud`
| Installs Nextcloud PHP dependencies, creates its MariaDB database/user, downloads and extracts the *latest* Nextcloud release tarball to `/var/www/nextcloud`, wires up PHP-FPM pool + nginx vhost/location, tunes PHP memory limit and opcache, and adds Nextcloud's own background-job and PNG-iCCP-cleanup cron jobs. Does **not** run the Nextcloud web/`occ` installer (admin account, `config.php`, trusted domains, Redis caching) — that step is currently manual. See `doc/TODO.adoc`.

| `mail`
| Postfix: TLS-only submission using the Let's Encrypt cert, SASL auth via Dovecot, alias + virtual-alias maps (vault-encrypted where they contain personal data), mail routed to Dovecot over LMTP, and RSpamd wired in as a milter on `mail.spam.milter_port` (`milter_default_action = accept`, i.e. fails open if RSpamd is unreachable). **The milter connection between Postfix and RSpamd is not working correctly yet** — under active troubleshooting, see `doc/TODO.adoc`.

| `imap`
| Dovecot core/IMAP/LMTP/Sieve. Deploys Sieve-pipe scripts that call RSpamd's ham/spam learning API so users can train the spam filter via IMAP move-to-folder actions.

| `spam`
| RSpamd: installs the package, wires it to the shared Redis instance, configures `actions.conf` and the controller web UI (password-protected via a vault-encrypted `htpasswd`, reverse-proxied through nginx at `spam.<domain>`). Not yet fully working end-to-end — the Postfix milter connection is currently broken (see `mail` above) — and **DKIM signing/key-generation, SPF, and several other RSpamd module configs are present as templates/scripts but are commented out** in `roles/spam/tasks/main.yml`, so outbound mail is not currently DKIM-signed either. See `doc/TODO.adoc`.

| `upgrade`
| Ubuntu release upgrade (e.g. 24.04 → 26.04). Generic, not tied to any specific release: the target is read from `upgrade.target_release` (unset by default, so the role is a no-op until a host explicitly sets it), and the actual version to move to is resolved by Ubuntu's own `do-release-upgrade` tooling rather than being passed literally. Fully updates and dist-upgrades the current release first, then runs `do-release-upgrade` non-interactively (via `async`/`poll`, since the command can run for over an hour and briefly disrupts networking), reboots, and re-verifies the release afterwards. Deliberately **not** wired into any other playbook: `playbooks/upgrade.yml` tags its tasks `never`/`release-upgrade`, so it only runs when explicitly requested with `--tags release-upgrade` (`invoke run-playbook --playbook=playbooks/upgrade.yml --tags=release-upgrade`, after setting `upgrade.target_release` in the target host's `host_vars`).
|===

== Known inconsistencies worth double-checking

* `roles/fail2ban/files/jail.local` enables an `nginx-404` filter, but no corresponding `filter.d` definition is deployed by this repo; verify it exists in the target OS's fail2ban package before relying on it, or fail2ban may fail to start that jail.
* The `http` role's certbot handlers restart/enable a `certbot` **service** (a one-shot unit), not the `certbot.timer` that Debian/Ubuntu's certbot package uses for scheduled renewal — worth confirming automatic renewal is actually active on the host.
