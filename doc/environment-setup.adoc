The development environment is a single link:{url-docker} container, built from `.devcontainer/Dockerfile` on an `ubuntu:26.04` base — note that this is deliberately *ahead* of the 24.04 the target host runs, since it holds tooling rather than services.
All configuration for it is kept in the directory `.devcontainer`; there is no compose file, and the containers `molecule` tests in come from the host's own daemon over the socket described below.

== Host Setup

The Linux host should have the following packages installed (Ubuntu-based distro as example):

[source, bash]
----
sudo apt update
sudo apt install \
  --no-install-recommends \
    containerd \
    docker-buildx \
    docker.io
----

And - of course - the installation of link:{url-vscode}.

Intallation on link:{url-wsl} running *Ubuntu 24.04* works fine.

=== Hardware virtualization

`devcontainer.json` passes `/dev/kvm` into the container with `--device=/dev/kvm`, for the QEMU guest the deployment tests run in (`.claude/skills/testlab/`, see link:{url-doc-testing}). Two consequences worth knowing before the first start:

* **The container will not start on a host with no `/dev/kvm`.** Remove that `runArgs` line in that case; everything except the test VM works without it. Under WSL2 the kernel exposes KVM and nested virtualization has to be enabled on the Windows side.
* **The device's permissions are fixed up at container start**, by `.devcontainer/fix-kvm-perms.sh` in `postStartCommand` alongside the Docker GID fixup below. If `vm.sh` reports `/dev/kvm` is not readable or writable, that script has not run — run it by hand rather than recreating the container.

=== Docker Mounts

The controller node maps configuration files from the host to provide the same environment as on the host.

[cols="h,m,d", options="autowidth"]
|===
| Bash config | `~/.bashrc` | Prompts, functions, etc.
| git config | `~/.gitconfig` | Aliases, etc.
| General config dir | `~/.config/` | Additional configuration settings
|===

The file `.devcontainer/devcontainer.json` may be adapted easily to accomodate other config files (e.g. `zsh` settings).

=== Docker

The container does not run its own Docker daemon. `devcontainer.json` bind-mounts the host's `/var/run/docker.sock` instead, and the Dockerfile installs only the Docker CLI to talk to it. This exists for `molecule`, which creates and destroys the containers the role tests run in — see link:{url-doc-testing}.

It is only needed for `invoke test-molecule`. Everything else, including `invoke lint` and `invoke test-static`, works without it.

The socket's group ownership depends on the host machine's `docker` GID, which can't be baked into the image, so `devcontainer.json`'s `postStartCommand` runs `.devcontainer/fix-docker-gid.sh` on every container start to add the user to a matching group. That only takes effect in a *new* login shell — a terminal already open when the container started keeps its old group list and gets `permission denied` talking to the socket. The Dockerfile also configures passwordless `sudo` for exactly this gap: `sudo docker ...` / `sudo molecule test` works regardless of session age, so that's the reliable way to invoke anything that touches Docker. `sudo` resets `PATH`, so use `sudo -E env "PATH=$PATH" invoke test-molecule` rather than a bare `sudo invoke test-molecule` (which fails with `invoke: command not found`).

=== Tooling not packaged for Ubuntu

Four tools are installed outside `apt` because Ubuntu 26.04 does not package them at a usable version, and all four are pinned in `.devcontainer/Dockerfile`:

[cols="h,m,d", options="autowidth"]
|===
| `ansible-lint` | `ANSIBLE_LINT_VERSION` | In a virtualenv at `/opt/ansible-lint` created with `--system-site-packages`, so it sees the same `ansible-core` and collections as the rest of the toolchain rather than a copy of its own. Ubuntu's own package carries no version pin and previously drifted out from under the repo.
| `yamllint` | `YAMLLINT_VERSION` | Alongside `ansible-lint` in the same virtualenv, which requires a newer release than Ubuntu packages.
| `ruff` | `RUFF_VERSION` | Release binary, fetched from GitHub.
| `molecule` | `MOLECULE_VERSION` | Installed into its own — fully isolated — virtualenv at `/opt/molecule`, because pip refuses to install into the system Python (PEP 668). The entry point is linked into `/usr/local/bin`.
|===

Keep all four in step with the versions installed by the workflows in `.github/workflows/`, so that CI and a local run use the same tools.
